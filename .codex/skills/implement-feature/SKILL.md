# 实施功能

完成用户授权的任务，同时让文档反映真实进展。分级、授权、状态和写作规则见仓库 [AGENTS.md](../../../AGENTS.md)。

## 先定位当前任务

- 标准模板读 `tasks.md`；多专题读对应篇的任务区。implementation/ 只作证据参考，不能代替任务清单。
- 确认目标、调用方、验收条件、已有批准和当前环境，复用现有模块与测试。
- 有外部依赖时，先找不依赖它的实现和验证工作；缺少生产条件不等于所有本地工作都暂停。
- 单项目小改动按 AGENTS 的轻量流程处理，不套完整项目模板。

## 实施与验证

1. 按任务范围修改代码，覆盖调用方、契约、配置和测试；不顺手整理无关模块。
2. 有新逻辑或修复缺陷时，执行能证明行为的相关测试。权限、持久化等边界不能只以编译通过代替验证。
3. 失败如实记录，修复后复验受影响范围；没有新改动或未解风险时，不机械重复全套测试。
4. 按 verify-change 记录阶段证据。已有用户指定的浏览器工具、真实环境和截图要求继续有效。

## 让进度跟上实现

每完成一个可验收子项，直接更新原任务，不在文末另建第二份“当前进度”清单。

保留任务的业务背景和预期行为，再说明完成了什么、实际验证到哪里、还差什么、谁来做下一步。不能把原任务替换成脱离背景的状态短句或链接列表。保留任务编号和原验收要求；下面是可选写法，不强制每项套长完成卡：

```markdown
### Task {编号}：{任务名称}

{谁遇到什么问题；希望系统完成什么行为}

**状态：** 部分完成（partial）。{一句话说明现在能做什么}

- [x] {已实现且有必要证据的子项}
- [ ] {仍需开发或验证的子项}

**下一步：** {具体动作；受阻时写所缺条件与责任方}
**验证结果：** {做了什么操作、观察到什么、还有哪些未验证；先给结论，再附复核链接}
```

已完成任务写“已完成（done）”并勾选；纯实现已结束但必要验证缺失，仍为部分完成。判断任务自身条件，不用全项目 Final 未完成作统一理由。

不把“README已更新、合规已检查”等编辑动作重复塞进每个业务任务。无需执行的检查写“不适用：原因”，不要留一个像未完成工作的空框，也不要勾成通过。

## 技术记录按需保留

简单任务在任务区和验证区能说清时，不额外建 implementation 文件。出现跨服务契约、迁移/恢复、重要取舍、故障复现或较长证据时，在已有记录中补充，或创建一份有明确主题的记录。

记录应包含：

- 关联任务、日期和适用环境。
- 行为变化与原因，必要的文件路径/符号名。
- 已执行的命令或操作、实际结果、证据位置和限制。

不强制逐函数贴前后代码、易过期行号或重复 Git diff。保留失败及修复记录，历史结论注明适用时间；更新当前说明，不能只在末尾追加“现已解决”。

## 收尾顺序

按 AGENTS 的“先更新文档，再汇报进度”执行：

- 更新原任务状态、勾选和证据；同步项目 README、受影响的 CONTEXT。
- 能力变化同步 FEATURES；feat/fix/perf 按要求更新 CHANGELOG，纯文档等不制造产品发布条目。
- 回读任务与汇总一致后，简短汇报结果和下一步。
- 用户要求完成整个范围时，继续可推进的后续任务；只完成一张任务卡不等于整单交付。
- 不因流程写有“提交”就自动执行 git commit、push、合并或部署；沿用用户明确授权。
