# Plan Project（规划项目）

用于规划新的项目或重构，创建项目文档结构。**这是 AI 在判断出改动级别后自动调用的 Skill，用户通常不需要手动触发**——判断标准见 `AGENTS.md` 的「改动分级」。

## 触发条件

- 链路改动：跨服务、影响契约或数据模型
- 治理改动：影响架构、安全、数据、生产环境
- 需要多人协作或跨会话的工作
- 需要评审的重要改动

## 跳过条件

- 单项目改动（单服务内部、不影响对外契约）——直接实现，不创建项目文档
- 纯讨论、探索性规划、"这个方案是否可行"类问题——直接对话给结论，不生成文档；用户明确要落地时再触发本 Skill

## 工作流

1. **确定项目信息**（AI 从对话上下文自行判断，只在真正不确定时才问用户）
   - 项目名称（kebab-case，如 `runtime-modeling-refactor`）
   - 项目目标（一句话描述）
   - 影响范围（哪些服务）
   - 改动级别（链路改动 或 治理改动）

2. **选择模板档位**（见下方「模板档位」，默认标准模板，满足升级条件才用多专题模板）

3. **创建项目目录、生成核心文档**（按选定档位，见下方对应模板）

## 模板档位

### 档位判断标准

- **默认：标准模板**——链路改动、大多数治理改动都用这个
- **升级：多专题模板**——满足以下任一条件时使用：
  - 方案规划过程中发现自然拆成 3 个以上互相独立、可以分别验收的子模块
  - 治理改动且预计跨多周/多阶段执行，一开始就能预见会拆分成多个子专题
- 不确定选哪档时先用标准模板；规划过程中发现装不下再升级为多专题模板

**独立子专题的判断标准：** 两个子专题"互相独立"，指子专题 A 的实现和验收完全不需要等子专题 B 完成——各自有独立的代码改动范围、独立的验收标准、独立的测试用例。如果两个模块高度耦合、必须一起上线，则不算独立子专题，应放在同一子专题内。

### 标准模板 → 多专题模板升级操作规范

升级是一个原子操作，必须按以下步骤完成，不允许"新文档建好、旧文档原地保留"：

1. **旧文档标注废弃**：在 `plan.md`、`tasks.md`、`verification.md` 顶部分别加一行：
   ```
   > ⚠️ 本文档已拆分为多专题模板，导航入口见 [README.md](README.md)，本文档不再维护。
   ```
2. **内容迁移**：将 `plan.md` / `tasks.md` / `verification.md` 的内容拆入对应的编号子专题文档（`01-xxx.md` 等），每篇子专题文档自带目标/方案/任务/验证/状态。
3. **更新 README.md**：
   - `模板类型` 字段改为 `多专题模板`
   - 加 `## 阅读顺序` 列表，列出所有子专题文档及各自一句话说明
   - README.md 的阅读顺序列表是**唯一纲领**，读者从这里进入任何子专题
4. **完成确认**：升级后所有信息入口只有 README.md，旧全局文档仅保留废弃提示。


### 标准模板

```
docs/projects/{YYYYMMDD}-{项目名}/
├── README.md           # 项目概览
├── plan.md           # 整体方案
├── tasks.md           # 任务拆分
├── verification.md           # 验证计划
└── implementation/             # 实现细节（后续创建）
```

### 多专题模板

```
docs/projects/{YYYYMMDD}-{项目名}/
├── README.md              # 导航 + 总体状态，含"阅读顺序"列表
├── 01-{子专题}.md          # 每个子专题自成一档：目标/方案设计/任务拆分/验证要求与记录/状态
├── 02-{子专题}.md
├── ...
└── implementation/         # 可选，更细粒度的逐次实现记录（跟子专题文档不是一回事）
```

每个编号文档内部结构统一：目标 → 方案设计 → 任务拆分 → 验证要求与记录 → 状态。单独看一个文档就能知道这块子专题干没干完，不用翻全局 `tasks.md`。README.md 的"状态"字段汇总所有子专题的完成度（例如："总体方案已确认；01/02 已完成；03 进行中；仅 04 待评审"这种粒度）。

## 标准模板 - 文档内容

### README.md 模板

```markdown
# {项目标题}

## 项目概述
- **时间：** {开始日期} 至 {预计结束日期}
- **目标：** {一句话描述}
- **负责人：** @{用户名}
- **模板类型：** 标准模板
- **状态：** 规划中 / 进行中 / done / partial / blocked / deferred（完成后用 `verify-change` 的四态判定，见该 Skill）

## 快速导航
- [整体方案](plan.md)
- [任务拆分](tasks.md)
- [验证记录](verification.md)

## 改动范围
- **影响服务：** {列出服务}
- **改动级别：** 链路改动 / 治理改动
- **预计工作量：** X 人天

## 关键决策
1. {决策1}
2. {决策2}
```

## 注意事项

- 项目名称使用 kebab-case，如 `runtime-modeling-refactor`
- 文档内容要具体，不要空洞
- 文件和函数要写清楚，便于后续查找
- 验证计划要明确，可执行
- 对于治理改动，创建后需要评审才能开始实现
- 规划中途发现标准模板装不下（子模块自然拆成 3 个以上），随时可以升级为多专题模板，把已有内容拆分迁移过去，不用推翻重来
