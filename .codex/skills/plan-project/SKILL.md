# 规划项目

把需求变成可执行、可验收的任务。项目已有文档时直接更新，不为同一目标另起一套。

分级、授权和文档写法以仓库 [AGENTS.md](../../../AGENTS.md) 为准。本 Skill 负责规划，不批准实施、提交或部署。

## 开始前

- 读 `docs/CONTEXT.md` 和当前项目入口，确认用户目标、已有决定、影响服务及尚未解决的问题。
- 按 AGENTS 的改动分级选择流程；纯讨论先给结论，单项目小改动使用既有轻量记录。
- 区分已知事实与设计建议。未知负责人、日期、预算或阈值明确写“待确认”，不要填示例值冒充承诺。
- 治理改动需要人工评审。已有批准在原范围内继续有效；新增安全/权限/契约冲突单独说明，先推进不依赖该决定的工作。

## 选择文档结构

| 情况 | 使用结构 |
|---|---|
| 默认：一个主要方案，任务可以集中阅读 | 标准模板 |
| 自然分成多个专题，集中成一篇会难以阅读 | 多专题模板 |

专题可以共享依赖，不要求彼此完全独立；写清哪些任务可以单独验收、哪些必须联合验证。文档拆成多篇不等于服务可以分别上线。不要仅因跨会话或文档变长就新建项目。

标准模板：

```text
docs/projects/{启动日期}-{项目名}/
├── README.md          # 当前结论、下一步和导航
├── plan.md            # 目标、方案、取舍、范围与批准
├── tasks.md           # 唯一任务进度
├── verification.md    # 验收要求、阶段验证、整体验收
└── implementation/    # 按需保留较长技术记录
```

多专题模板：

```text
docs/projects/{启动日期}-{项目名}/
├── README.md          # 当前结论、专题汇总和导航
├── 01-{专题}.md       # 当前进展、任务、方案、验证
├── 02-{专题}.md
└── implementation/    # 按需保留较长技术记录
```

多专题不再并行维护全局 plan/tasks/verification。使用已有目录和启动日期，项目名用 kebab-case。

## 写方案与任务

README 先用完整业务过程说明谁遇到什么问题、希望怎样操作、得到什么结果，再写当前能力和缺口。专题承接其中一段过程，每项任务独立交代背景与预期行为。技术约定写清参与系统、传递的信息和用途，不用“上述模块”让读者补上下文；详细路径与长证据放技术区。

每个任务应有明确的行为目标、改动位置和验收条件。任务太大时拆分实现、验证和外部依赖；不把所有功能都绑定到项目最终验收后才允许完成。

可按下列结构写，已有清晰格式直接沿用：

```markdown
### Task {编号}：{用户能理解的任务名称}

{谁遇到什么问题，为什么需要这项工作；本任务在业务过程中起什么作用}

**状态：** 待开始。
**完成标准：** {可观察的行为与必要验证}
**涉及位置：** {关键模块或文件；只列与本任务有关的内容}

- [ ] {要实现的行为}
- [ ] {要验证的场景}

**开发与验证进度：** 尚未实施、未执行验证；实施后在这里先说明实际结果与限制，再给复核链接。
**下一步：** {由谁做什么；受阻时说明所缺条件}
```

- 纯设计、代码完成、测试通过、人工批准和生产上线是不同事实，分别说明。
- 状态含义与汇报顺序使用 AGENTS 的统一约定，不在模板里另造一套。
- 不使用不能渲染的 `[/]` 复选框；勾选只用 `[ ]` / `[x]`，进行中用文字表达。
- 明确真实环境、模型调用、数据使用与外部发送的授权边界；不把规划视为授权。
- 验证计划写清预期行为和最低证据，性能/预算门槛需要负责人冻结时保留该依赖。

## 升级已有模板

仅在确有阅读收益时升级，保留原任务编号、验收条件和历史证据：

1. 把方案、任务和验证迁入专题；保持阶段验证与整体验收分开。
2. 更新 README 导航及所有被移动的链接。
3. 在被替代的全局文档顶部注明“不再维护”和新入口；迁移完成后只保留导航提示，不留下两套活跃状态。
4. 回读确认内容没有遗漏。不要因为某阶段完成就将仍有效的设计移入 archive。

## 交接与检查

- 任务覆盖用户要求，未悄悄缩小范围；未知项有具体问题或条件。
- 不看聊天、不跳链接，读者能说清需求、成果和下一步；README、任务与验收要求一致，链接可达，无模板占位。
- 治理批准未获得时，不启动依赖该批准的实施；不重复索取已经给出的批准。
- 按 AGENTS 先更新文档、再汇报。方案获准后衔接 implement-feature；不止步于“可以继续”。
