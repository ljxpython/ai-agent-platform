# 验证改动

证明行为符合约定，并说明证据的边界。项目状态与汇报顺序统一采用仓库 [AGENTS.md](../../../AGENTS.md) 的规则，不另造判定标准。

单项目改动使用匹配风险的测试和轻量记录，不强制生成项目验收文件。纯文档调整核对内容、链接和一致性，不冒充新增产品测试。

## 先找验收要求

| 项目结构 | 任务进度 | 验证记录 |
|---|---|---|
| 标准模板 | tasks.md | verification.md |
| 多专题模板 | 对应专题的任务区 | 同篇的验证区；联合验收放指定专题 |

先读本次任务的验收条件、已有证据和最新修改。不要为多专题项目补建一套全局 tasks/verification。

## 选择够用的验证

| 边界 | 需要证明什么 |
|---|---|
| 单服务内部 | 相关行为测试；适用的类型/lint检查 |
| 跨模块或服务 | 单元/契约、集成与最短完整链路；链路改动至少一条E2E |
| 权限、隐私、审计 | 允许和拒绝场景；真实调用链或锁定的契约证据 |
| 持久化、重启、恢复 | 实际重启/恢复后的行为；只校验复制文件不能当作恢复服务通过 |
| 治理改动 | 全部关键链路，适用的安全/性能测试、回滚及负责人评审 |
| 真实CI、盲测或生产范围 | 对应真实环境/独立人员的证据；本地或合成测试不能替代 |

联调前遵循仓库 Worktree 规范，从所属 local-stack 登记读取端口和资源，不复制模板中的固定端口。用户指定 browser-skill、截图或特定链路时按要求执行；仅有API测试不能声称前端验收通过。

## 阶段验证（Phase）

任务开发过程中，运行与改动相关的最小充分测试集。测试可以失败；保留实际结果，修复后补复验。阶段证据写入阶段区，随后更新原任务。

每份记录说明：

- 关联任务、代码/配置版本或差异、环境与身份范围。
- 命令/用户操作、预期行为、实际结果；先用正文说清测到了什么、没有证明什么。
- 日志/截图链接只用于深入复核；任务区也要有能独立读懂的结果摘要，不要求读者跳转后才能知道是否通过。

允许一次测试覆盖多个任务，也允许一个任务经历多轮验证。**按验收条件能否追溯到证据判断覆盖，不能要求“记录条数等于完成任务数”。** 重叠测试数量不相加冒充唯一样本数。

可沿用已有清晰格式；简短记录例如：

```markdown
### {日期} · {任务编号与验证主题}

- 范围：{版本/环境、身份和数据类别}
- 执行：{真实命令或操作}
- 结果：{实际观察；失败及修复分开写}
- 证据：{日志/截图链接}
- 未覆盖：{缺少的条件；没有则省略}
```

## 整体验收（Final）

先核对已批准的当前验收范围。前置实现任务和必要阶段验证应具备证据；**联合Final任务本身不需要预先勾成完成**。待用户批准的范围调整不能自行当作延期，外部阻塞也不能靠删除验收项消除。

1. 检查任务、README、验证记录及CONTEXT的状态是否一致，逐项确认前置条件。若仍有可推进工作，继续处理，新增证据仍记阶段区。
2. 依据完整验收计划执行所需单元、集成、端到端和适用的性能/安全/恢复验证；不机械重跑没有变化且仍有效的证据，但需标明复用版本和理由。
3. 独立记录联合验证结果，不复制阶段记录或上一项目结果冒充本轮Final。
4. 问题修复后复验对应场景；失败未解决不标项目完成。所有当前范围必要条件满足后，再标记Final任务和项目完成。

Final记录只保留实际执行内容：版本/环境、测试结果、关键链路、未解决问题及结论。没有跑的项目写“未验证”，不填“全部通过”。

## 判定与汇报

沿用 AGENTS 的中文状态及稳定标识（done/partial/blocked/deferred）：

- 单项自身验收通过即可完成；其它专题待验收不自动将它变回未完成。
- 代码存在但证据不足时，区分“尚未核对”和“确认未实现”，不要凭缺少记录断言没做。
- 有可推进的开发/补证时，不能把全部剩余事项概括为外部阻塞。
- 真实环境缺失先完成不依赖它的工作，再说明条件、责任方及解除后的验证动作。
- 关闭检查后的构建通过，只能说明该命令通过；默认构建失败、warning和已知限制如实保留。
- 合成样本、独立人审、真实调用和mock分别标注；不自动批准阈值、独立盲测资格或生产上线。

最后先更新任务状态/勾选与证据，再同步README及CONTEXT并回读，之后才向用户汇报。用户要求的整个范围尚有可执行工作时继续推进，阶段通过不是结束理由；Git提交、合并或部署仍需相应授权。
