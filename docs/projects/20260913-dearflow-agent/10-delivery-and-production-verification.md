# 10 实施顺序、交付门槛与生产验收

## 目标

先验证底座和边界，再逐项交付业务能力。每个阶段均有进入条件、实际产物和退出门禁；功能、Skill、供应商和部署拓扑分别记录验证结果，不用“Demo 能跑”代替生产可用。

## 工作上下文

- **总入口：** [项目总纲与交接规则](README.md)。独立开发本章时先读总纲，不以聊天历史代替依赖证据。
- **实施阶段：** P0—P7 的实施顺序与汇总验收；能力详细任务仍归对应专题。
- **必读前置：** [总纲](README.md) 接续状态、[01 第一轮实施包](01-architecture-and-boundaries.md)、[08 F／C 明细](08-web-and-platform-contracts.md)、[07 K 台账](07-skills-migration.md)，以及当前阶段所需专题证据。
- **输入 → 输出／对接：** 各专题真实验收与未决项 → 当前阶段结论、支持范围、下一切片、生产发布门禁；不能代替具体任务测试记录。
- **当前切片／最近证据：** P0/P1 当前授权后端范围 done，见 [05 部署验证](implementation/05-p0-p1-deployment-verification.md)；浏览器验收本轮后置。
- **下一任务：** 按 P2 执行包推进研究与交互基础，需要前端对接时提前告知。
- **结束回填：** 更新本章任务／验证／状态及此处游标，按总纲登记最近 implementation 记录、契约变化和下一精确任务；部分切片通过不勾选整章完成。

### 3. 测试分层与实际执行入口

以下为**实施后**的验证命令规划，本轮未执行。新测试路径见各专题，创建时沿用现有 pytest marker：`integration`、`durable`、`e2e`。测试用例应验证行为、信任边界或故障，不为每个纯提示词函数机械写断言。

Runtime 命令在 `apps/runtime-service/` 执行：

```bash
uv run pytest tests/services/dearflow_agent -m "not integration and not durable and not e2e"
uv run pytest tests/services/showcase_demo tests/runtime tests/middlewares -m "not integration and not durable and not e2e"
uv run pytest tests/integration/test_dearflow_external_tasks.py -m integration
uv run pytest tests/durable/test_dearflow_external_tasks.py -m durable
uv run pytest tests/e2e/test_dearflow_skills.py -m e2e -k K01
```

最后一条要求未来测试参数 ID 显式使用 K01—K23；每次只跑当前迁移技能，最终再运行完整受支持集合。P0／P1／P3 同样补与其行为相符的真实引擎 integration／durable 测试，不只跑外部任务用例。

Platform 命令在 `apps/platform-api/` 执行，优先已有契约／安全／网关回归，加本项目新增的边界用例：

```bash
uv run pytest tests/test_runtime_gateway_runtime_contract.py tests/test_runtime_gateway_files.py tests/test_runtime_gateway_images.py tests/test_runtime_delegation.py tests/test_runtime_catalog_delegation.py
```

Web 命令从仓库根执行，脚本来自当前 package.json／Playwright 配置：

```bash
pnpm --dir "apps/platform-web" test:run
```

### 5. 性能基线：先定义测量，再承诺指标

P0 记录 CPU／内存、磁盘、网络、worker 数、模型与供应商、输入规模。将平台自身开销与外部模型耗时分开统计，不能把外部生成时间混入“网关延迟”。

拟定首轮负载：10 个并发根 Run，其中 3 个使用 Ultra；每个 Ultra 的子任务遵守 02 的上限，整体容量同时受执行 worker 策略限制。使用固定工具服务和真实供应商分别测，后者受账户配额约束。

拟定门槛，P0 实测后冻结或写明调整原因：普通控制 API 在上述固定负载下 p95 服务端处理开销不超过 500 ms（不含 LLM／供应商等待）；正常可终止本地执行在取消请求后 10 秒内清理；连续 30 分钟运行后活跃资源可回落到稳定基线；长文件流不按完整文件大小额外占内存。实际基线不满足时修复或缩小首发并发声明，不能直接改测试阈值标绿。

### 6. 上线、升级与回滚门禁

1. 首发冻结 Runtime worker 与执行主机／持久卷拓扑、依赖锁和镜像 digest；不在本轮规划中执行部署。
2. 迁移采用显式命令和可审查脚本，不在应用启动时偷偷建表。Platform catalog、Runtime 私有任务／技能／记忆表分别明确所有者；只做必要增量变化。
3. 发布顺序：兼容字段／资源先准备 → Runtime 新能力关闭状态发布 → Platform 契约／授权 → Web → 定向验证 → 按已验收 Skill 逐个启用。开关属于服务策略，不允许客户端自行开启未完成能力。
4. Context v2 先验证旧审批恢复；无可靠版本信息的存量运行／审批须排空后升级。回滚也不能把 v2 请求送给只懂 v1 的服务，必要时维护窗口停止新增而保留读取。
5. 产物采用不可变引用和版本化路径；回滚应用不删除新文件／新记忆。数据库备份与文件备份必须能对齐到可恢复版本；演练缺文件、坏 hash 和任务未终结情形。
