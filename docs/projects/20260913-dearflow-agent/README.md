# Dear Agent 总纲：Deep Agents 能力迁移、专属前端与生产化

## 项目概述

- **启动日期：** 2026-09-13；结束日期在架构 Spike 后排定。
- **目标：** 在现有平台内交付以 Deep Agents 为底座的 DearFlowAgent，完成需求理解、技能选择、工具执行、受控委派、结果核验和回答／文件交付，并建设 Dear Agent 专属前端，成为使用真实生产链路的 Agent 展示。
- **方案修订：** 2026-09-14 第二版；项目目录保留启动日 20260913，不新建一套重复项目文档。
- **负责人：** 用户负责方案评审与业务验收；AI 协助实施和验证，具体团队分工待排期。
- **改动级别：** 治理改动，包含跨服务契约、执行隔离、持久化和生产部署。
- **状态：** 进行中。P3 后端复用与追踪字段修复已落地，39项回归及真实父取消通过；完整成功运行仍触发Worker超时，已发现事件持久化显著滞后，外部观测导出未验收，P3为partial。完成项、代码路径、成功与失败证据见 [P3 执行包](phases/P3-子%20Agent%20展示与观测.md) 和 [07 实施记录](implementation/07-p3-subagents-and-observability.md)。前端按用户要求只交接，未修改代码；不声明生产联合验收完成。
- **预计工作量：** 见 10 的阶段估算；以 23 个 Skill 逐个验证为前提，不把文件复制量当作交付工作量。

## 已确认约束

1. 主 Agent 使用 `deepagents.create_deep_agent`；通过 LangChain Middleware、LangGraph State／Store／interrupt／SDK 实现能力。
2. 只迁移 DeerFlow 的能力和适用资源；不依赖、内嵌或运行 `deerflow-harness`，不引入它的网关、RunManager、全局配置系统或兼容 Adapter。
3. 业务唯一根目录为 `apps/runtime-service/src/runtime_service/services/dearflow_agent/`，Graph 通过 `graphs/` 注册。
4. Showcase 仅作为范式和回归样例。新业务不放入 Showcase，也不导入其私有实现；跨服务内 Agent 的真实共用能力才进入现有公共层。
5. 浏览器操作不做；产品入口只做现有 `platform-web`。IM、TUI、外部客户端产品不在范围内。
6. 人机交互采用官方 interrupt／HITL／resume；保留自由文本、选项、表单和“先问再做”的保护效果，不迁移 DeerFlow 的 END＋新用户消息续跑路径。机制对比与 Runtime 实现见 02 §6，前端／网关接入见 08 §11。
7. 保留全部 23 个公共 Skills 的迁移项，逐个迁移、逐个验证、逐个启用；不以基础设施完成替代 Skill 验收。
8. 子 Agent 当前阶段优先复用普通 `SubAgent`／`task`、官方 namespace 和已有前端展示；修复现有关联、状态和恢复展示缺陷。独立 child Run、单任务取消、完整用量归属和结果验证在现有能力不足时后置。
9. 消除附件与 Showcase 的专属耦合，补齐文件输入／输出、执行环境、恢复和运维能力。
10. 不自动提交、创建分支、部署或操作生产数据。
11. Dear Agent 前端业务放在 `apps/platform-web/src/modules/dear-agent/`；以现有 Chat 为基线快照复制首发所需展示与交互代码，复制后两边独立演进。网络请求继续放在 `apps/platform-web/src/services/`，鉴权、公共 API 类型与平台基础设施继续共用；禁止跨模块依赖 Chat 业务组件，具体清单见 08 §7。
12. 第一轮实施先搭前后端贯通的真实框架；之后按已批准阶段逐步补齐功能。用户可逐章发起实现，章节间以本总纲、工作上下文及验收记录接续，不依赖聊天记忆。

## 总纲如何使用：每次从这里进入

**本文件是唯一项目入口。** 01—09 是能力专题，不是“一章全部做完才能读下一章”的流水线；10 的 P0—P7 才是施工顺序。尤其 04 文件、08 前端／契约的基础切片必须在 P1 交付，09 的长任务必须在媒体技能前交付。不能等到读第 08 章才开始前端，也不能在 P1 一次创建所有未来模块。

**怎么使用这张表：** 开始一个阶段时，先读“主入口／对应章节”，再只读“主要任务编号”指向的切片；完成后回填专题任务、10 章阶段表和本总纲接续状态。阶段之间是交付顺序，专题之间可以提前阅读，但不能把“读过章节”当成“阶段已完成”。

### 阶段执行包与文档优先级

`phases/P0—P7-*.md` 是每个阶段的单一执行入口。按顺序阅读 `README.md → 当前阶段执行包 → 执行包列出的专题小节 → implementation/最近记录`，不需要在 01—10 之间自行拼接上下文。

文档优先级固定为：

1. **当前阶段执行包**：决定本次做什么、读什么、验收什么。
2. **01—10 专题文档**：长期有效的架构、契约和能力设计事实源。
3. **`implementation/`**：实际改动、测试证据、阻塞和下一步记录。
4. **本 README**：全局状态、阶段顺序和交接游标。

阶段执行包只引用专题，不复制设计正文；若执行包与专题不一致，以专题为设计事实源，并在实施记录中修正阶段包。阶段完成后只回填状态和链接，不复制任务清单，避免多份事实源漂移。

### 跨章节执行与交接约定

1. 开始：重读仓库 `AGENTS.md`、涉及服务的现行规范、本总纲与当前章的工作上下文；用实际源码／测试确认先前记录仍有效。方案记录不替代源码事实，旧聊天回复不作为唯一上下文。
2. 定界：报出“阶段 Pn＋专题任务 ID＋本次切片＋前置通过证据”。任务 ID 必须带专题前缀，例如 `04/W01` 与 `08/W01` 是不同任务，禁止只写 W01。F／K 也写 `08/F1`、`07/K01`。
3. 开发：按 08 C 表检查契约生产方／消费方；只创建本切片实际需要的目录／文件。官方 API 在实施时再查 MCP 文档与锁版本，不能把调研时的签名当永久承诺。
4. 验证：每个切片至少跑对应确定性测试和实际受影响链路；前端存在时必须从 Dear Agent 路由验证。前置尚未真实联调只能记 partial／blocked，mock 不算闭环。
5. 交接：`implementation/{序号}-{专题或阶段}-{主题}.md` 记录本次范围、代码位置／关键符号、最终接口版本／样例链接、变更理由、实际测试与证据、剩余任务／阻塞、下一步精确任务及必读文件。按 `implement-feature`／`verify-change` 写入，不复制设计全文。
6. 回填：更新该章任务、验证、状态及“工作上下文”的当前切片／下一任务／最近证据；跨章切片逐章登记。同步本总纲游标、10 阶段结论、08 契约落点及 `docs/FEATURES.md`。设计改变时直接修改生效专题，并记录受影响已批准项是否需要再次评审。

每次交接都要让下一位开发者仅靠仓库文件回答：**做到了哪里、用的哪些接口、哪些测试确实通过、还缺什么、下一步改哪些文件**。实现记录缺失或任务与源码不一致时先纠正记录，不根据推断勾选完成。

后续可以直接这样发起：

```text
阅读 docs/projects/20260913-dearflow-agent/README.md 和 01-architecture-and-boundaries.md，
按当前已批准范围实现 P1 基础切片；先核对 P0 证据，再按章节依赖完成前后端闭环并回填状态。
```

这是接续用语示例，不是本轮实施授权。明确批准过的范围内不反复请求确认。

## 已批准方案与后续验收约束

| 决策 | 推荐基线 | 理由／影响 |
|---|---|---|
| D1：执行模式 | 纳入，底座先以 Standard 打通；模式随后统一接入版本化 Context | 模式有产品价值；不能绕开现有 Context 哈希、模型能力或授权 |
| D2：子 Agent | 当前采用普通同步 `SubAgent`，复用官方 namespace 和 Chat 展示；AsyncSubAgent／独立 child Run 后置 | 只有未来出现真实长任务和单独控制需求时再启动 Spike |
| D3：长期记忆 | 纳入，先明确 CRUD 与检索，再加自动提取；优先官方 Store，一致性缺口按 06 的 Spike 冻结唯一事实存储 | `memory=` 仅加载文件；Store 接口不能未经验证就假设提供原子更新 |
| D4：后台范围 | 长耗时生成／远程任务恢复纳入；Goal 自动续跑和定时任务建议后置 | 前者支撑音视频等已要求 Skills；后两者暂无明确主动运行场景 |
| D5：23 个 Skills | 全部保留；外部客户端桥接技能改为 Web 平台操作语义；部署须显式审批 | 保留业务意图，同时遵守仅 Web、不运行 DeerFlow、不开放宿主执行的约束 |
| D6：生产首发 | 使用隔离执行 worker 和持久工作区，冻结已验证部署拓扑 | 多副本、远程执行和跨机挂载必须有证据；不宣称任意拓扑天然可用 |

D5 的 `claude-to-deerflow` 原始含义与“无外部客户端入口、无 DeerFlow 运行依赖”不能原样同时满足。07 提供明确的功能改写与验收差异，保留该 Skill 的清单及来源身份；需要人工确认该解释，不能在实施时默默删掉或伪称原样等价。
