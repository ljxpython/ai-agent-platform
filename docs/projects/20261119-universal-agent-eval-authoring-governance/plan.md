## 1. 业务目标与现状依据

开发者把获准会话和业务素材交给 EvalFlow，由 EvalFlow 整理评测题、辅助修订、管理独立题库，并按用户选择对已有回答评分或发起新运行。会话交付与出题不以来源 Agent 的名称、当前可运行状态、完整工具清单或重新执行能力为前提。

这不等于绕过资料获取：首次采集仍需来源权限及可用的数据通道；来源接口不可用、正文未取得时如实报告采集失败。已经取得的获准资料和独立题库，不因目标 Agent 暂不可运行而失去后续处理能力。

以下为2026-11-19立项时本地源码评审确认的原问题，当时尚未执行远端产品或模型验证；当前已实施的行为与实际证据见 tasks.md、verification.md，不将这些旧行为继续描述为修复后的现状：

- EvalFlow 的 `eval_platform/evaluation_assistant.py::SYSTEM` 写有固定退款规则、`sales.csv` 与 `refunds.csv` 示例；`eval_platform/work_items.py::Proposal.model_json_schema()` 另有 `sales-v1` 示例，会进入模型输入。
- Agent 平台的 `apps/platform-api/src/platform_api/modules/evaluation/materials.py::process_materials_background` 采集获准会话，再转发给 EvalFlow 创建工作项；该主路径没有直接调用评测目标快照接口。可选执行证据与会话正文应分别处理。
- 重新执行路径存在图限制：EvalFlow 的 `eval_platform/config.py::EvalConfig.authorized_graph`、Platform API 的 `apps/platform-api/src/platform_api/modules/evaluation/targets.py::configured_target` 只接受 `dearflow_agent`；Runtime 的 `apps/runtime-service/src/runtime_service/webapp.py::graph_capability` 只为该图附加评测能力。这些是现有适配限制，不是通用出题的业务前提。
- 平台已有 `evaluation-target/v1` 快照、运行绑定和漂移检查。Runtime 的 `apps/runtime-service/src/runtime_service/observability/evaluation_target.py::capabilities` 所列工具主要来自动态知识与 MCP 配置，不是完整有效工具全集。
- 当前 Case v3 拒绝 `no_write`；`clarification_requested` 检查 `request_information` 工具中断，普通文字追问需使用语义评价。

后续远端完整输入检查还确认共享 BusinessFacts 评分步骤存在固定退款口径，一并去除。固定真实模型批次已覆盖工程、文本和真实退款正例；“历史单测倒灌”的因果来源，以及“任何工程输入都会触发退款幻觉”，仍不能作为已证实结论。

## 2. 两步推进与完成边界

### 第一步：修复提示词与 Schema 描述污染，建立回归基线

对应 Task 1、Task 4.1。在 EvalFlow 内清理通用提示中的固定业务假定，覆盖 `SYSTEM`、默认提示词、Schema 描述与最终上下文。保留格式校验、答案防泄露、来源区分、多轮规则、审批阶段和必要数值核算。

验证非退款工程、纯文本及确有退款要求的对照素材。不得无依据增加业务事实，也不得因去污染丢失输入明确要求的业务规则。第一步不扩展服务间协议或执行后端；阶段通过不代表全项目完成。

### 第二步：解耦通用出题、历史评分与按需运行

对应 Task 2、Task 3、Task 4.2。先在 EvalFlow 保证受支持格式的会话可独立转成题库：不按来源 Agent 名称拒绝，不要求选择在线运行目标，不新增必填 `AgentManifest`，不以取得完整工具全集为出题或发布门槛。

能力描述是可选的出题参考；无法查询、服务离线或信息不完整时，说明适用范围与未核实的执行条件。资料足够时继续出题、修订和独立发布。业务事实本身不足时保留草稿并澄清，不伪造预期答案。

用户选择评分已有回答时，仅核对所选指标所需证据；选择重新执行时，再核对目标权限、调用协议及该用例所需能力。使用现有可用目标验证运行隔离，不预设必须新增一个非文件型 Agent。两个平台服务先做接口核查；只有实际请求暴露缺口且变更范围获准，才实施相应修改。

文件类与纯文本类是两类出题素材，不要求来自两个已接入运行协议的 Agent。原方案将完整能力契约、新非文件型 Agent 执行及跨服务改造设为通用出题的必做项，本轮按用户确认撤销这一前置关系，改为按实际需求启动的执行接入分支。

### 本项目不做

- 不侵入 MLflow 上游 `mlflow/`，不新增推理网关或平行目标身份体系。
- 不把来源标识当作执行准入条件，不要求每个来源 Agent 实现专用评测接口。
- 不改写历史题库或 Run，不通过跳过认证、来源授权或执行审批实现解耦。
- 不承诺模型必定正确、自愈必定成功，或未经接入验证的目标已支持重新执行。

## 3. 第一步的出题与校验规则

1. **通用规则与业务素材分开。** 通用提示和 Schema 描述不固定领域文件、金额、月份或答案；获准素材和测试夹具可以包含真实业务实例。“数字格式不等于业务正确性”等规则保留为通用表述。
2. **核对最终模型输入。** 检查 `EvaluationAgentExecutor.build_prompt()` 拼入的提示词、Schema、素材、历史讨论和修复反馈。业务证据保持不可信数据属性，不能提升为权限指令。
3. **预期有独立依据。** 用户确认的规则与获准原始资料用于建立预期；旧助手回答和工具返回不自动成为标准答案。题面保留必要条件，隐藏预期与评分结论不进入被测输入。
4. **断言服从现有契约。** 仅有逐字要求时使用精确答案断言；文字澄清采用明确逐轮标准的语义指标，工具式澄清才使用 `clarification_requested`。零工具预算不与必须调用澄清工具的要求并用。
5. **文件与安全断言表达准确。** Case v3 不使用 `no_write`，按场景使用 `artifacts.absent`、受保护资源检查与 `executed` 工具约束。拒绝执行不等于禁止触发审批的 `attempted` 调用。`/workspace/work/` 只约束适用的文件适配器。
6. **有界修复与草稿保护。** 复用已有校验和预算；当前入口最多 3 次候选尝试、执行器 `max_steps=8` 作为核对基线，不增加隐式重试。失败、取消、权限失效或草稿更新不得覆盖已有版本。

## 4. 第二步的职责与检查时机

| 动作 | 必要检查 | 能力与目标信息如何使用 |
|---|---|---|
| 会话交付、出题、修订和独立发布 | 来源/资产权限、用途、脱敏、资料与题目结构、业务质量 | 来源标识用于追溯；可选能力辅助出题，目标离线或不支持重跑不阻止这些动作。 |
| 对已有回答评分 | 评分操作权限及每个所选指标的证据 | 文本证据满足时可做文本评价；缺工具/文件证据的指标明确不可判定或不支持，不伪造通过，不妨碍其他证据充分且可独立评价的指标。 |
| 显式发起新运行 | 当前执行权限、调用协议、用例所需资源与证据能力 | 复用适用的快照、目标绑定、漂移、审批、停止与恢复检查；兼容性按能力判断，不把固定 Agent 名称当作长期准入依据。 |

### 4.1 可选能力参考与题库独立性

优先复用现有资料、适配器元数据或已提供的能力接口；用户确认的能力说明标明来源，仅作出题参考，不等同服务端授权。没有这些信息仍可根据完整会话出题；未知能力不等于无工具，历史调用也不证明当前权限。

有来源支持的工具或产物要求可以保留为题目执行需求；当前目标是否满足留到新运行时核对。信息不足时在候选说明或现有适当字段中标明待核实条件，不凭空指定工具，不把“未选择运行目标”伪装成业务缺口而阻断发布。具体字段先核对现有契约，不为了规划新增一套能力协议。

结构和业务质量检查始终保留。只有初始业务资料不足、无法建立可靠题目时才澄清或保留草稿；仅运行目标不可用，不影响内容完整题库的独立发布。来源授权到期后，已有题库按自身权限管理；重新取源另查当前来源授权。

### 4.2 评分与运行按需校验

能力校验只覆盖用户选择的操作与用例实际依赖，不要求所有目标提供文件、工具调用或完整 Trace。普通文本评分不强制要求工具/产物证据；涉及调用尝试、拦截和实际执行的指标分别核对相应证据。

发起新运行前才查询该目标必要的当前能力；能力接口离线不触发执行权限绕过。缺少新运行必需信息时拒绝本次启动并说明原因，题库及其他操作保持可用。适用的目标快照继续保护配置身份与运行绑定，不能为了移除 Agent 名称限制而直接删除协议、权限和证据检查。

### 4.3 按实际缺口决定跨仓修改

默认修改 EvalFlow 的配置加载、上下文、候选、发布/评分与执行分支，核对是否把运行目标检查提前带入非运行动作。Agent 平台已有资料交付接口优先复用。

Task 3.3 核对现有来源接口和运行适配路径，记录所选操作、实际可用能力及缺口。若现有接口满足需求，`platform-api` 与 `runtime-service` 不改代码；若实际需要接入其他图而被名称限制或缺证据协议阻挡，再提交具体范围、兼容方案和验证要求评审。未启动的新增接入不作为核心出题验收阻塞，也不宣称已完成通用执行支持。

## 5. 验收原则

- **独立出题：** 在获准资料已取得或资料获取通道可用的条件下，文件类、纯文本类素材即使没有完整能力清单、目标暂不可运行或未支持重新执行，仍能完成资料交付、AI 出题、审核采纳和独立发布。本项目复核及采纳由用户明确委托 AI 执行，身份如实记录，不冒称独立人审。
- **结构与质量：** 所有被接纳内容通过 `Proposal.model_validate()`、`Case.preflight()` 与业务检查；当前目标可运行性单独表达。检查业务保真、逐轮生效点、独立预期和防泄密，空用例集不算出题成功。
- **证据评分：** 用已有回答验证文本指标；缺工具/产物证据只影响依赖它们的指标，不误报通过。
- **新运行：** 用现有支持目标验证显式启动、当前权限和适用的兼容检查。新增非文件型执行接入仅在需求与范围获准后补验，不作为通用出题前提。
- **模型统计：** 固定 10 次真实出题，文件类/纯文本类素材各 5 次，首稿通过率大于 80%。分别报告修复后和修复条件成功率、失败、耗时及 Token，不承诺自愈 100%，不外推任意 Agent。
- **兼容与回退：** 保留旧题库、冻结版本及 Run 事实。按实际改动验证应用/配置回退、权限和隔离；若追加跨服务接入，补相应契约、执行、安全和回退验证。性能验证按新增开销决定，适用性与门槛在实施评审确定，不因尚未新增能力接口强制进行三服务压测。

唯一实施进度见 [tasks.md](tasks.md)，具体样本与证据要求见 [verification.md](verification.md)。
