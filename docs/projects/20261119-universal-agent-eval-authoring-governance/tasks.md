## 第一步：去除提示词与 Schema 描述污染

### Task 1：恢复通用出题规则并校准现有契约

开发者提交不同业务的会话时，出题助手应依据该会话出题，保留用户确认的业务规则与逐轮要求，不附加固定的退款、金额或文件假定。已有退款业务素材仍须得到正确处理。

**状态：** 部分完成（partial）。
**完成标准：**

- 检查最终模型输入，清理 `SYSTEM`、默认提示词与 Schema 描述中的固定业务假定；覆盖 `sales-v1` 等 Schema 示例，不将测试夹具中的合法业务素材当作污染删除。
- 保留答案防泄露、来源区分、多轮约束、必要数值核算及审批阶段等通用原则；只在需要数值核算的场景要求出题助手调用计算器，不要求无计算任务或被测 Agent 调用同名工具。
- 生成规则符合当前 Case v3：不使用 `no_write`；区分文字追问与 `request_information` 中断；零工具预算仅适用于题目明确要求，且不与工具式澄清并用。
- 复用既有校验、最多 3 次候选尝试及执行器 8 步预算，不增加隐式重试；无效候选不进入可发布内容，失败、取消和草稿变化不覆盖已有版本。
- 通过 Task 4.1 的完整输入检查、针对性回归与质量核对；相关既有测试无新增失败，既有失败单列证据。

**涉及位置（相对 EvalFlow 仓库）：**
`eval_platform/evaluation_assistant.py`、`eval_platform/agent/prompts.py`、`eval_platform/work_items.py::Proposal.model_json_schema()`、`eval_platform/agent/agent.py::EvaluationAgentExecutor.build_prompt()`、`eval_platform/agent/graph.py`、`tests/test_authoring_assistant.py` 及相关契约测试。只修改核实与本任务有关的位置，不预设重构状态机。

## 第二步：通用出题、已有回答评分与按需运行解耦

### Task 2：让会话与可选能力参考独立进入出题

开发者提交获准会话后，应能在 EvalFlow 出题、修订和发布题库。来源 Agent 的标识用于追溯，不要求其在线、已接入重新执行协议或提供完整工具清单。

**状态：** 部分完成（partial）。
**完成标准：**

- 会话交付、创建工作项、出题、修订和独立发布不以固定 Agent 名称、在线执行目标、完整工具全集或必填 `AgentManifest` 为门槛；保留原来源/资产权限、用途和脱敏约束。首次采集仍需可用的数据通道，取得资料后不再把目标是否可运行当作处理前置。
- 可选能力信息复用现有素材、配置或接口并标明来源及完整性；缺失、过期或查询失败时按未知处理，不声称无工具或已获授权，不阻断资料充分的出题。
- 会话已证实或用户确认的业务要求与工具/产物需求可作为出题依据；缺少当前目标兼容性只标明执行条件未核实，不全局拒绝候选、修订或发布，不伪造新的 Schema 字段。
- 业务事实不足时澄清并保留草稿；内容完整但运行环境不可用时仍可独立发布。来源到期后沿题库自身权限操作，重新取源另查授权。
- 验证出题失败、取消、并发编辑、资料权限及历史题库兼容；运行配置或能力查询故障不能破坏已有资产操作。

**默认涉及位置（EvalFlow 仓库）：**
`eval_platform/evaluation_assistant.py::advance_authoring`、`eval_platform/work_items.py`、`eval_platform/work_item_jobs.py::advance`、`eval_platform/config.py`、`eval_platform/contracts.py` 及相关上下文、发布和配置消费者。沿现有结构修复，不预设新增能力协议。

**仅核对的 Agent 侧位置：** `apps/platform-api/src/platform_api/modules/evaluation/materials.py` 及现有交付接口；发现实际缺口才转入 Task 3.3 的变更评审。

- [ ] 核对资料交付、出题与发布是否误依赖执行目标，记录实际调用关系。
- [ ] 在 EvalFlow 解耦运行前置检查，支持无能力参考时正常出题及发布。
- [ ] 回归可选信息失败、来源权限、修订/发布与历史资产行为。

**开发与验证进度：** 已移除共享配置对 dearflow_agent 的全局限制，新发布题库不再硬编码运行图要求；TaskStore 仅在选中用例需要新执行时解析当前目标。出题、版本、授权和任务相关阶段回归 156 项通过（4.25 秒）。来源授权仍保留，尚未完成两类真实交付到独立发布，任务部分完成（partial）。

### Task 3：按所选操作检查证据与运行兼容性

用户可选择只出题、评分已有回答或启动新运行。三种操作分别检查自己的必要条件，重新执行的限制不得提前阻断资料交付与题库管理。

**状态：** 部分完成（partial）。
**完成标准：**

**Task 3.1：形成通用的素材与断言验证样本。**

- 冻结文件类与纯文本类素材、业务规则及预期行为，不要求它们来自两个已支持重新执行的图；不将 `support_agent` 名称或新 Agent 注册作为前提。
- 按真实任务与素材选择指标，保留多轮规则生效点，区分文字/工具式澄清与安全调用阶段。
- 文件、工具要求需有素材或已确认规则依据；没有完整工具清单时不臆造权限，当前目标兼容性留到新运行时验证。
- [ ] 完成两类素材、断言、缺口与指标组合的针对性回归。

**Task 3.2：分开已有回答评分与显式新运行。**

- 只评已有回答时不启动 Agent，不查询与所选指标无关的执行能力；文本证据足够可评价文本。
- 缺少工具、文件或检索证据时，依赖这些证据的指标明确不可判定/不支持，不误报通过；其他可独立评价且证据充分的指标仍可处理，整体不得掩盖缺失。
- 用户明确启动新运行后，才核对当前执行权限、调用协议、目标及用例实际所需资源/证据。复用适用的快照、绑定、漂移、审批、停止、恢复与幂等，不要求无关能力。
- 目标离线、协议不兼容或能力不足仅拒绝该新运行，题库仍可读、修订和发布；不按来源 Agent 名称决定出题资格。
- [ ] 验证历史评分不重跑、证据不足准确呈现，以及新运行检查只在显式动作发生后执行。

**Task 3.3：核对接口缺口，按需决定执行接入改动。**

- 用现有支持目标核对新运行链路，并记录来源交付、评分与新运行分别依赖哪些接口。现有名称限制作为适配缺口记录，不直接删除全部准入校验。

- 本次已确认调整：核查为必做，新增非文件型 Agent 完整执行不再是通用出题的验收门槛。未启动的新增接入记录为范围外条件，不勾成已实现；若后续获准纳入，则同步任务和验收，未完成前不宣称该扩展已交付。
- [ ] 记录实际接口核查结论及是否需要跨仓修改；有获准扩展时追加可独立验收的子项。
