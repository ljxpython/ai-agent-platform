# 06 自定义角色、授权委托与防提权

## 目标

判断固定角色何时不够，以及引入自定义角色需要改变哪些数据、接口、前端和治理流程。默认不做通用 RBAC 编辑器；先说明进入条件。

## 方案设计

### 6.1 什么时候真的需要自定义角色

固定角色足够的例子：项目管理员管成员，编辑管 Agent，执行者运行；平台超级管理员/运维/只读职责稳定，组织没有合规分离要求。

必须有真实组合需求才进入自定义角色，例如：

- 客服只能读取会话、不能执行；模型运维能改全局连接、不能看项目对话；审计员能跨项目看治理事件、不能写配置。
- 一个项目需要让“Agent 编辑 + 项目审计只读”组成岗位，但不想给成员管理。
- 企业要求职责分离，创建账号的人不能给自己或同级授予高风险权限。

如果只是 executor 名称不准确、模型资源范围未理顺，先修固定权限；自定义角色会把问题藏进配置而不是解决根因。

### 6.2 推荐的数据模型

```text
PermissionDefinition(code, resource, action, scope_type, risk_level, active)
RoleDefinition(id, key, name, scope_type, system_managed, version, status)
RolePermission(role_id, permission_code)
RoleBinding(subject_type, subject_id, role_id, scope_type, scope_id, expires_at, created_by)
```

当前 `users.platform_roles` 与 `project_members.role` 是字符串/单角色字段。迁移需决定：

- 平台系统角色与项目自定义角色共用一套 binding，还是保留两套表。
- 旧 role 字段是否保留只读兼容、如何一次性生成系统 RoleDefinition。
- 角色是否可继承、是否允许多角色绑定、冲突如何合并。
- 权限是否可以 deny。推荐第一版纯 allow，工具限制仍单独使用已有拒绝并集，不把 deny 混入通用 RBAC。

### 6.3 绑定与提权保护

授予角色必须同时检查：执行者有 `role.bind`，且被授予角色的有效权限集合不超过执行者被允许委托的上限。不能只检查“能改成员”就允许任意 role key。

例：project_admin 能授予 project_editor；不能把一个包含 project.member.write、project.runtime.policy.write 的自定义角色授给自己或同事，除非明确拥有该权限的委托权。Kubernetes RBAC 的 `escalate` 防护说明了“管理角色定义”和“把角色授予别人”是不同权限。

推荐首期：

- 系统角色不可修改、不可删除；自定义角色只在允许 scope 创建。
- 角色不能跨平台/项目 scope 绑定。
- 高风险权限（用户角色、凭据、服务账号超级权限、项目接管、私有 Thread takeover）进入受保护集合。
- 禁止给自己增加权限，或至少要求二人审批；本期更简单的固定角色可先禁止。
- 角色/绑定变更写审计，保存操作者、目标主体、旧集合、新集合、原因和请求 ID。
- 删除角色前必须无 binding；停用角色不立即改变已运行任务，但新请求重新计算。

### 6.4 前端治理界面不是第一步

需要自定义角色时，前端至少新增角色列表、权限说明、scope 选择、风险提示、影响主体预览、绑定/撤销、不可编辑系统权限和提权错误。权限 code 不能直接裸露给普通用户当复选框；应按资源/动作分组并显示数据范围。

若暂时没有真实角色管理员，保留后端迁移脚本/管理 API 不等于必须做 UI。先用固定角色完成治理，避免建设无人维护的权限编辑中心。

### 6.5 多角色合并与撤销

推荐 allow 并集、scope 交集约束：用户在项目 A 的多个角色权限合并，只对 A 生效；平台角色不能替代项目绑定。撤销一个角色后重新计算有效权限；前端缓存失效，后端新请求即时生效。

不能把“角色移除”当作删除数据；已创建资源和审计保留。角色版本变更是否影响旧绑定、是否快照到绑定记录，待 D26 决定；权限定义 bug 修复一般应影响新请求，重大收紧需要发布说明和回滚策略。

### 6.7 工程量影响

本期不做自定义角色，不增加工程量。若未来被真实岗位证据触发，最小项目角色后端方案预计增加 8—14 人天；完整角色中心预计增加 15—30 人天，届时另立治理项目。

## 任务拆分

### Task G1：固定角色是否足够的业务验证
- **改动内容：** 以真实岗位/项目清单对照 02 动作矩阵，统计无法表达的组合，不以“以后可能需要”作为理由。
- **代码位置：** `apps/platform-api/tests/test_iam_policy_engine.py`、用户/项目角色数据导出脚本（只读）。
- **预期结果：** 明确“不做自定义角色”或列出最小不可替代组合。
- **验证项：** 至少两类平台岗位、三类项目岗位、服务账号和撤权场景；输出差异表。
- **状态：** `[ ]` 作为后置观察项；不阻塞本期实现。仅记录固定角色无法表达的真实岗位证据。

### Task G2：自定义角色（条件任务）
- **改动内容：** 只有 D23 批准且 G1 有证据时，设计迁移、RoleDefinition/Binding、委托上限和管理 API。
- **代码位置：** `modules/iam/`、identity/users/projects service、migration、前端治理模块（是否实现 UI 单独审批）。
- **预期结果：** 角色定义、授予和资源 scope 分离，不能自助提权。
- **验证项：** role escalation、跨项目绑定、删除有 binding、角色停用、最后治理者恢复、服务账号高风险角色。
- **状态：** `[ ]` deferred；不属于本期任务，满足触发条件后另立项目。
