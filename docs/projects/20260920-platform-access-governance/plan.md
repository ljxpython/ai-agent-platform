# 全平台权限治理 — 范围与待讨论方案

## 背景

工具权限管理的讨论引出了“管理员与普通用户能看哪些页面、执行哪些操作”的全平台问题。该范围超出当前工具治理，需要独立评估。

现有代码已有角色、权限 helper、路由守卫和后端 IAM。此次只阅读部分入口确认可复用机制，不声称已完成全平台安全审计，也不预设需要重建权限系统。

## 目标

1. 明确平台角色与项目角色的职责、适用范围和组合行为。
2. 为每个页面列明菜单可见性、URL 访问、读取、写入及数据范围。
3. 保证前端交互与后端授权一致，隐藏菜单不能替代后端校验。
4. 明确权限变更、项目切换、会话缓存更新及无权限页面的行为。

## 待讨论问题

- 平台超级管理员、运维、只读角色与项目管理员、编辑、执行角色分别可以做什么？不能只按“管理员/普通用户”二分。
- 平台角色与项目成员身份如何组合？跨项目管理和接管是否需要显式动作及审计？
- 哪些页面所有项目成员可读，哪些页面仅治理人员可见？同页面不同按钮权限如何表达？
- 页面级读取权限与具体资源范围如何对应，避免“能打开页面就能看全库”。
- 权限变更后多久生效？切换项目、旧浏览器标签页和缓存中的权限如何更新？
- 当前系统是否需要可配置角色/权限管理界面？先确认真实需求，不默认建设通用 RBAC 编辑器。
- 工具禁用例外作为已交付能力如何纳入总矩阵，而不重做其 Runtime 执行协议？

## 方案边界

优先复用已有 IAM、路由元数据和菜单组件。后续先产出“角色 × 页面 × 操作 × 数据范围”矩阵，评审后才决定代码变化。不提前选择新依赖、权限引擎或数据库 schema。

预期链路为 platform-web → platform-api。是否需要调整 Runtime 信任契约、角色存量数据或部署流程，必须有盘点证据再扩围；当前暂无已确认契约变更。

## 实施阶段（全部后置）

1. 全量页面/接口/角色盘点，形成当前行为与产品期望差异。
2. 讨论权限矩阵和生效语义，人工评审具体实施方案。
3. 按批准范围实现前后端控制与必要数据迁移。
4. 多身份集成、E2E、安全和回滚验证。

## 风险与依赖

- 菜单隐藏与服务端授权可能不一致：逐页面关联实际接口并验证直接请求。
- 多角色/项目切换可能产生意外权限：基于真实身份组合构造负向测试。
- 若调整角色授予或数据范围，可能扩大既有权限：先盘点存量，再评审迁移。
- 后续以工具治理专项的实际交付为输入；该依赖方向不反转，不阻塞当前专项。
