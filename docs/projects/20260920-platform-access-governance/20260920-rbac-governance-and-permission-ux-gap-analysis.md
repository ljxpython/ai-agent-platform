## 1. 触发背景 (Context & Trigger)

在平台管理后台为测试人员新建了一个账号 `Test`，并赋予平台“运维”（`platform_operator`）身份。然而该账号登录 `platform-web` 后，进入工作台却发现无法发起任何对话，输入框和相关操作按钮全部处于置灰不可用状态。

这一现象引发了根本性疑问：
> **“当前的这套权限系统，到底合不合理？为什么平台运维连发一条消息都不可以？”**

经过对系统架构、前后端代码契约及用户实际操作路径的深入排查，特此将关于权限体系的设计合理性、现实落地缺陷及后续演进方案总结归档。

---

## 2. 权限体系的架构合理性剖析 (Why It Is Designed This Way)

从后端架构与企业级安全合规（ISO 27001 / SOC 2）视角分析，当前系统的底层权限模型设计**在理论上不仅是合理的，而且是符合规范的企业级双层 RBAC 架构**。

### 2.1 双层隔离模型 (Two-Tier Model)

平台明确切分了两个完全正交的权限平面：

```
┌─────────────────────────────────────────────────────────────────┐
│                     治理平面 (Platform Plane)                   │
│  角色: platform_admin / platform_operator / platform_auditor    │
│  权限域: 系统监控、集群资源、全局模型网关、服务账号、全局审计日志  │
└────────────────────────────────┬────────────────────────────────┘
                                 │ 逻辑正交，不自动穿透
┌────────────────────────────────▼────────────────────────────────┐
│                     业务平面 (Project Plane)                    │
│  角色: owner / admin / developer / operator / viewer            │
│  权限域: Agent 编排、会话 (Threads)、对话流式执行、工具调用算力  │
└─────────────────────────────────────────────────────────────────┘
```

1. **治理平面角色 (Platform Roles)**：
   - `platform_admin`：拥有整套系统的最高管理权限；
   - `platform_operator`（运维）：负责监控实例健康度、排查链路故障、管理 Runtime Gateway 节点和模型供应商配置；
   - `platform_auditor`（审计）：负责合规审查、导出调用日志与安全合规记录。
2. **业务平面角色 (Project Roles)**：
   - 依赖以“项目 (Project)”为租户边界的独立成员体系；
   - 只有在具体项目中被赋予了具备写权限的角色（`owner`、`admin`、`developer`、`operator`），才拥有 `project:threads:write` 和 `project:runs:execute` 权限。

### 2.2 为什么“运维”默认不能发对话？（合理性依据）
- **最小权限原则 (Principle of Least Privilege, PoLP)**：
  在生产环境或多租户企业架构中，运维人员负责的是“基础设施运转”，而不是“业务使用”。
- **算力成本与额度隔离 (Cost Attribution)**：
  发起 Agent 对话会直接消耗项目的 Token 额度、并发配额和工具执行算力。如果赋予平台运维全局隐式执行权，会导致各业务项目的核算账单混乱。
- **数据合规与业务隐私 (Data Privacy & Compliance)**：
  业务项目中的对话、记忆上下文、提示词工程属于各业务方核心资产。平台运维不应默认拥有刺探业务对话内容的权力。

**结论**：双层 RBAC 模型在架构分层、安全红线和租户隔离上是**科学且必要**的，绝不能简单把平台运维粗暴提升为所有业务项目的默认管理员。

## 3. 现存缺陷与可用性断层深度批判 (The Gaps & Flaws)

虽然底层架构设计站得住脚，但**在产品化落地与前端体验呈现上，存在严重的设计断层，甚至可以说是极度反人类的“哑巴体验”**。

### 3.1 缺陷一：认知断层与无解释的“哑巴置灰”
- **现象**：
  在绝大多数工程师的惯性思维中，“运维（Operator）”往往等同于或仅次于系统管理员（比如 Kubernetes 集群管理员）。当测试用户以“运维”身份登录后，直奔对话工作台，迎面而来的却是置灰的按钮。
- **致命问题**：
  前端界面**没有任何解释性反馈**。
  - 没有 Hover Tooltip 提示；
  - 没有状态 Banner 提示；
  - 没有任何引导文案说明“您在当前项目中未获得执行权限”。
- **后果**：
  用户无法判断究竟是“权限不足”、“系统报错”、“后端崩溃”还是“账号被封”，陷入强烈的认知困惑与挫败感。

### 3.2 缺陷二：用户创建与项目授权的流程割裂
- **现象**：
  超管在平台的用户管理页面（`UserCreatePage.vue`）开通新账号时，只能填写用户名、邮箱、密码，并选择全局平台角色（如运维）。
- **致命问题**：
  创建用户的流程中**完全缺失了项目初始化的步骤**。
  - 创建完用户后，超管必须手动记住：退出来、找到对应项目、进入项目设置、进入成员管理、搜索刚才的用户、再次分配项目角色；
  - 如果超管漏掉了这一步，这个新用户登进平台就会变成一个**“平台幽灵”**——可以进系统，但进到任何项目里都处于未授权的只读/不可用状态。

### 3.3 缺陷三：文案歧义火上浇油（已于此前修复）
- **现象**：
  此前 `UserMenu.vue` 中，若用户未绑定邮箱，系统使用了通用回退键 `t('common.unavailable')`，直接在头像下拉框下方大字显示“暂不可用”。
- **致命问题**：
  当一个权限受限的新用户看到自己的资料卡上写着“暂不可用”，同时界面上所有交互按钮又全部置灰时，100% 的用户都会得出同一个错误结论：“这个账号失效/被禁用了”。

## 4. 后续改良方案 (Proposed Improvement Roadmap)

鉴于当前团队正全力攻坚核心业务需求（如 Runtime 工具解析与前端链路对齐），权限系统的改良宜分为轻量体验补齐与中长期流程优化两阶段推进。

### 阶段一：轻量体验补齐 (Phase 1: Transparent UX Feedback - 低成本高回报)

不改变现有的后端 RBAC 架构，仅在前端补全透明度与引导：

1. **禁用控件补充解释性 Tooltip**：
   - 对话输入框置灰时，提示：
     > *“当前账号在当前项目仅有只读权限，无法发起对话。如需操作请联系项目管理员分配权限。”*
   - “新对话”按钮置灰时，悬浮展示相同的权限说明。
2. **项目级全局权限状态 Banner**：
   - 当检测到当前登录用户在当前选中的 `activeProject` 中无任何有效成员身份（或仅为 `viewer`）时，在页面顶部显示一条柔和但明确的提示条：
     > *“您正在以访客/只读身份浏览项目【XXX】。无法执行修改与会话操作。[申请加入项目] / [切换工作区]”*

### 阶段二：用户生命周期与开通向导一体化 (Phase 2: Onboarding Wizard)

打通平台管理与项目成员管理的孤岛流程：

1. **用户创建向导 (User Onboarding Modal)**：
   - 在平台管理后台新增用户弹窗中，增加可选步骤：`关联默认项目`；
   - 允许超管一站式勾选要将其加入的项目（如 Default Demo Project），并直接指定其在项目内的初始角色（如 Developer）。
2. **内置“公共沙箱/体验项目”机制**：
   - 系统可保留一个全局只读或轻量可执行的“体验沙箱”项目，所有新建用户无论何种角色，首次登录均默认进入该沙箱，能够直接体验基本对话与 Agent 能力，避免“登进来啥也干不了”的尴尬。

### 阶段三：运维专属视图与透视能力 (Phase 3: Operator Perspective)

为平台运维（`platform_operator`）提供更符合其工作职责的专属工作台：
1. 默认首页应引导至**系统运维监控 / 运行时健康看板 / 日志排障中心**，而非业务对话页；
2. 若运维需要验证特定 Agent 是否健康，提供专门的“健康拨测/连通性探测”专属工具，而非以普通租户身份参与业务对话。

---

## 5. 结论与追踪

- **结论总结**：
  底层的双层 RBAC 设计符合标准，**无需重构后端鉴权内核**。痛点的根本原因是**前端未做权限透明化感知**与**开户流程未做项目关联**。
- **落地排期**：
  当前优先级集中在运行时工具链改造上，此文档作为后续开展“平台易用性与权限交互专项”的标准事实源 (Source of Truth)。待核心需求交付后，按【阶段一】和【阶段二】逐步落地实施。
