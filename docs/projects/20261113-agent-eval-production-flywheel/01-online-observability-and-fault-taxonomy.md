# 01-线上监控、质量度量与故障归因捕获体系

> 更新：2026-11-14｜状态：本轮批准范围已完成（done）｜原始目标中的暂缓项继续保留。

## 这篇要解决什么问题

用户觉得Agent的一条回答不对，团队首先需要知道：是哪条回答、当时发生了什么，以及问题是否值得继续调查。用户没有反馈时，系统也应有办法发现运行异常或抽查回答质量。

这篇负责“发现问题并留下可解释的记录”。Agent平台是用户对话和运行任务的地方；EvalFlow是整理测试资料、运行评测和查看结果的平台。两边需要把同一次对话对应起来，但记录到异常线索不等于已经确认故障。

## 希望完成的使用过程

1. **用户反馈或系统发现线索。** 用户在某条消息上提交意见；运行服务也记录失败、取消或疑似重复调用。
2. **找到具体对话与执行。** 保存问题来源、发生时间和关联标识，稍后把反馈与详细运行记录对应起来。详细运行记录在技术实现中称为Trace。
3. **只对获准回答做抽查。** 管理者批准用途、字段、模型与预算后，系统抽样评分，记录评分失败或资料缺失。
4. **让团队判断下一步。** 受控页面展示统计；需要复现的问题进入专题02的授权、审核流程。只有另获批准，才接告警或尝试自动干预。

这四步是目标流程，不代表已经全部开放。下文的Worker指实际执行Agent任务的后台进程；“旁路”表示只观察和记录，不改变Agent的执行结果。

## 目前能用什么，还缺什么

消息反馈可以保存、修改和撤回，并关联到对应运行。旁路探针会记录疑似重复调用；受控统计页能分开说明完成、取消、预期拒绝和证据缺失，数据不足时不会强行给出均分。

巡检的授权、队列、预算、发布和撤权功能已通过本地验证。真实模型评分组件与使用评分替身的完整发布测试分别留有证据，不能混称为真实自动巡检。网关硬上限说明尚缺，自动采样保持0；正式性能、Grafana告警和自动停止循环按用户决定暂缓。

### Task 1.0 — 先约定问题记录写什么，以及监控可以增加多少开销

- [x] **已完成（done，本轮批准范围）**

同一条回答在聊天页面、Agent执行服务和评测平台里有不同的编号。如果记录对不上，团队即使收到一条“回答有问题”的反馈，也可能找不到发生问题的那次对话。因此需要先约定三个系统传递哪些信息，并确定增加监控后可以接受多少等待时间和资源消耗。

**本轮验收范围：** 本轮完成问题记录字段、分类和统计口径核对；正式性能、容量及开销门槛按用户决定暂缓，不阻塞其余功能。

**原始完整目标：** 问题记录能说明属于哪次对话、哪次执行、何时发生、来自用户反馈还是系统检测；真实故障、取消和正常拒绝不会混为一谈。性能测试有事先批准的开销、延迟和丢失标准，可以据此判断监控是否适合启用。

**开发进度：** 问题记录的归属、来源、分类及统计分母已统一；取消、正常拒绝、故障和证据缺失分别呈现。正式监控开销和容量门槛按用户决定暂缓。

**已经验证到哪里：** 字段与分类测试、真实取消回执、反馈关联以及受控质量汇总页面均有证据。早期开关各40次的开销观测仅作参考，不声称达到正式性能标准。

**下一步由谁做：** 本轮功能及联合验收已完成。后续由负责人安排生产、独立评审及其他已暂缓范围。

### Task 1.1 — 让问题记录可靠到达评测平台，重复和缺失都能解释

- [x] **已完成（done，本轮批准范围）**

用户提交反馈后，评测平台可能暂时不可用；Agent的运行记录也可能晚于反馈到达。系统需要保存已经收到的信息，稍后继续关联，而不是丢掉反馈、重复生成评价，或因为监控故障拖住Agent回答。

**本轮验收范围：** 补齐异常、取消、断流、服务失联和未保存Trace的处理；已接收反馈可恢复、去重，缺失明确显示。性能压测暂缓。

**原始完整目标：** 源平台先保存反馈，评测平台再异步接收并关联运行记录。重复提交不会产生重复评价，暂时失败会有限重试；无法补回的记录明确显示缺失，不能把缺失算成“没有问题”。

**开发进度：** 反馈先持久保存，再异步关联；重复投递、丢响应、暂时失联和晚到Trace可以对账。未保存的Trace明确计入缺失，不能把缺失当正常，也不靠重新运行Agent来补历史。

**已经验证到哪里：** 恢复、去重、丢响应、重试上限、调度公平、多子任务归属和缺失统计测试通过。真实三题回归中取消无Trace仍取得持久执行回执；新批次反馈在页面显示已关联1条原生Trace。

**下一步由谁做：** 本轮功能及联合验收已完成。后续由负责人安排生产、独立评审及其他已暂缓范围。

### Task 1.2 — 让用户反馈能找到对应回答，并能修改或撤回

- [x] **已完成（done）**

用户发现回答不合适时，需要在那条消息上留下反馈，之后也能修改或撤回。团队应当知道反馈针对哪次回答，而不能只收到一条脱离对话的“差评”；反馈本身也不能直接被当成已经确认的系统故障。

**做到什么才算完成：** 反馈只能写到当前用户有权访问的消息上；重复提交、修改和撤回都有明确结果。相关运行记录尚未到达时仍能保存反馈，后续再关联到评测平台的原生评价（Assessment）。

**开发进度：** 消息反馈、幂等保存、修订/撤回、跨项目拒绝、无Trace时保存及页面状态刷新已经实现。原生评价关联和撤权失效也已完成本地功能验收。

**已经验证到哪里：** API和组件测试覆盖了权限、重复请求、缺少Trace及页面刷新。浏览器实际跑通了保存反馈、授权、关联评价和撤权；后端核对了原评价失效，源服务失联和恢复后的处理也有记录。

**下一步由谁做：** 本任务范围内没有剩余开发项。真实生产资料能否导出仍由专题02的授权政策决定；反馈功能完成不等于允许自动外发原对话。

### Task 1.3 — 发现Agent可能在反复做无效工作，但先不自动终止

- [x] **已完成（done）**

Agent可能重复调用同一个工具，也可能在几个工具之间来回切换。重复并不一定是错误：正常轮询、等待审批和有界重试也会重复。因此首先要收集疑似无进展的线索，看看检测器会误判哪些正常情况。

**做到什么才算完成：** 探针识别重复或交替调用，记录相关执行范围和检测结果；只标记“疑似”，不新增模型调用，也不改变原任务的结果。校准报告同时写出检测正确、误报和漏报的情况。

**开发进度：** 旁路探针、稳定调用指纹、统计分母和疑似信号已经实现。观察与校准证据的输出满足本任务要求；自动干预属于Task 1.6，尚未启用。

**已经验证到哪里：** 8个受控场景覆盖重复只读、交替调用、合法轮询、结果变化、有限重试、并行进展和审批恢复。结果为2次正确检出、4次正确排除、1次误报和1次漏报；这不是线上准确率估计。

**下一步由谁做：** 本任务的旁路实现已完成。若后续希望自动停止执行，负责人需要先决定误报/漏报的接受条件，再按Task 1.6验证干预；不能因为探针可运行就直接开启停止功能。

### Task 1.4 — 抽查已授权的回答，帮助发现用户没有反馈的问题

- [x] **已完成（done，本轮批准范围）**

用户不会指出每一次错误，所以希望系统能抽查部分回答，用评分模型帮助发现质量问题。抽查会使用资料、产生费用，必须限定用途、字段、模型和预算，不能从一次反馈授权推导出任意评分权限。

**本轮验收范围：** 完成授权、队列、评分、发布和撤权的功能与本地链路验证；使用真实模型的受控组件验证与测试替身分开记录。缺网关硬上限说明的真实自动抽样启用暂缓，sample_rate保持0。

**原始完整目标：** 项目管理者批准项目/Agent范围、允许的输入输出、评分模型、有效期和预算后，系统按比例选取回答、排队评分。超时、未知用量或预算耗尽时保守停止；每次调用和发布结果前都重新检查授权。

**开发进度：** 独立巡检授权、持久队列、去重、运行预算、评分后复核和原生结果发布已完成。本地合成验证把真实模型组件与替身链路分开记录；自动采样仍为0。

**已经验证到哪里：** 真实评分组件已完成正负样本；新增集成测试用合成源授权和固定评分替身，实际写入MLflow SQLite，确认分数与Token指标、重启不重复评分，评分中撤权不发布。巡检25项测试通过，既有页面授权/撤权截图保留。缺网关硬上限说明的真实自动抽样启用继续暂缓。

**下一步由谁做：** 本轮范围及联合验收已完成。明确暂缓的启用和独立评审仍由负责人后续安排。

### Task 1.5 — 让团队看懂质量统计，并在获准后接收告警

- [x] **已完成（done，本轮批准范围）**

团队需要知道有多少回答被纳入检查、实际评分了多少、哪些失败或缺资料。正常取消、预期的权限拒绝和真实故障要分开看；用户没有反馈，也不能被当成“满意”。

**本轮验收范围：** 完成鉴权页面的故障、正常取消、预期拒绝、反馈及巡检统计，解释分母与缺失；Grafana接线和真实通知继续暂缓。

**原始完整目标：** 在有访问权限的页面展示清楚的统计对象与分母，样本不足时不下均分下降结论；不同项目和授权批次不能越权查看。需要告警时，经过批准的接收端能收到最小必要摘要，并能处理重复和恢复通知。

**开发进度：** 已鉴权的EvalFlow汇总页能区分正常完成、取消、预期拒绝、证据错误及资料缺失；反馈分母无法获得时明确显示不可计算，小样本不显示平均分。

**已经验证到哪里：** 汇总与畸形资料测试8项通过，页面组件3项通过；浏览器截图57显示6个任务、7次执行、5次完成、1次取消、2条证据错误、1条缺Trace，均有统计口径说明。撤权批次从巡检统计中排除，刷新失败清除旧值。Grafana及通知外发仍暂缓。

**下一步由谁做：** 本轮范围及联合验收已完成。明确暂缓的启用和独立评审仍由负责人后续安排。

### 2. 信号、故障与严重度

F1–F5 保留为分析分类，不替代现有底层错误码。候选允许多标签；分类不是自动处置指令。

| 分类 | 可用证据 | 必须区分的情形 |
| --- | --- | --- |
| F1_STEP_EXHAUSTION | 权威预算耗尽事件；无进展调用线索 | 预算耗尽不自动等于死循环；慢响应不等于耗尽 |
| F2_TOOL_MALFORMED | 不存在的工具、参数校验失败 | 上游超时、权限拒绝、服务不可用另记原因，不能统称工具幻觉 |
| F3_WORKFLOW_VIOLATION | 未授权副作用、审批前执行、实际跨项目泄漏证据 | 正确拒绝审批/越权请求是防护有效；被阻止的攻击尝试单独计数 |
| F4_INSTRUCTION_DRIFT | 当前有效约束、完整相关会话与违背证据 | 用户修改了原约束时按最新约束判断；点踩只生成待确认线索 |
| F5_GROUNDING_FAILURE | 实际检索依据、引用解析与输出矛盾证据 | 无检索上下文不能直接计算 Faithfulness；一般事实错误不硬套 RAG 分类 |

每条信号最少记录：`event_id`、`schema_version`、`signal_source`（human/rule/judge）、`signal_type`、原始错误码、候选类别、`confirmation_status`（suspected/confirmed/dismissed）、证据引用、检测器版本、发生/接收时间。严重度依据已证实影响独立确定；确认的未授权副作用按安全事件处理，但本功能不替代原审批/权限强制执行。

运行结果另存 completed/failed/cancelled/timed_out/interrupted/unknown 及原始状态。审批等待、用户拒绝和主动取消按预期场景解释。断流后查询权威 Run/停止回执，不能用客户端连接状态判定执行终态。

### 3. 反馈契约与多标识关联

Web 沿用现有 Vue 聊天组件，提供轻量点踩与可选原因；原因是用户意见，不直接写成 confirmed fault。可撤回/修改反馈；历史版本和操作者可审计。

拟新增反馈入口挂接现有 Thread/Run 授权链。具体 HTTP 路径在 Task 1.0 核对路由规范后冻结，不沿用「任意 trace_id 可写」入口。请求包含客户端幂等 ID、Thread/Run/message ID、rating、可选 reason/comment；tenant/project/actor 由认证上下文解析，不由客户端自由指定。服务端校验对象归属、反馈权限、文本长度和请求频率。

关联记录区分：
- 业务：tenant_id、project_id、thread_id、run_id、message_id；审批恢复可产生多个 Run。
- 排障：platform_trace_id / W3C trace context；不冒充 MLflow Trace ID。
- 评测：mlflow_experiment_id、mlflow_trace_ids、可选 span_id、assessment_ids；一个业务对象允许关联多个 Trace。
- 取证质量：关联状态 pending/linked/unavailable、缺失原因和有限等待期限。

已有 mlflow_tracer.py 将平台 ID 作为 metadata/tag 注入；实际 MLflow ID 由服务端受限查询解析。原生 Assessment 保存 HUMAN/CODE/LLM_JUDGE 来源与理由；tags 仅存检索投影。反馈更新按事件/反馈版本对账，不覆盖其它人的评估。

Trace 未到达、未启用追踪或取消后缺 Trace 时仍可保存业务反馈；如实标 unavailable，不能编造 Trace 或把缺失解释为无违规。链接打开后由目标服务再次授权，URL 中只传标识，不携带访问令牌或原文。

### 4. 可靠采集及旁路失败策略

采用「源侧可靠记录 → 异步投影到 EvalFlow → 回执对账」：
- 源侧只持有反馈、最小信号、关联和导出资格；审核/题库发布真源在 EvalFlow，见专题 02。
- 对反馈，源侧持久化成功后才返回已保存；对运行信号，复用持久运行事实及补扫能力。无持久事实可恢复的事件必须标明采集覆盖限制，不能宣称全部异常可恢复。
- 以 event_id/反馈版本设唯一约束；至少一次投递配合目标幂等键。远端超时先查原 ID，不能新建重复 Assessment。
- 采用有界重试、退避、最大积压和失败暂存/人工重放；记录丢弃、过期、延迟、重试及缺失数。
- 评分、MLflow 或投影故障不能阻塞主 Agent 执行；本地反馈保存失败明确返回失败。安全授权与脱敏失败则拒绝导出，不能按旁路可用性原则放行。
- 禁止每个 span 同步查询业务库/远端服务。存储实现先核对既有能力，缺口才在 `Agent: apps/platform-api/migrations/` 增量迁移，不预置独立消息平台。

### 5. 无进展检测：先观察，再干预

同工具、归一化同参数连续出现三次，只能产生 suspected 线索；跨进程摘要使用稳定指纹，不用 Python 内置 hash() 作为持久去重标识。摘要限制在项目/Run 范围，敏感参数不写入指标或开放日志。

校准样本必须包含合法轮询、重读且结果变化、有界重试、并行工具、审批恢复、重复只读无进展，以及 A→B→A 循环。关联工具类型、输出/状态变化、进展和重试原因，避免全局窗口混入其它子任务。

阶段 1 只打标，不抛异常、不增加模型调用、不发送新的终止指令。已有预算机制继续工作。阶段 4 才评估干预：先冻结误报/漏报接受条件，再按工具/Agent 小范围灰度；需与停止回执、在途副作用及收尾语义兼容。干预开关独立于采集开关，关闭后恢复原执行路径。没有可靠证据或安全停止能力时维持旁路。

### 6. 抽样巡检与统计口径

唯一采样配置：`sample_rate`。部署默认 0（关闭）；经授权启用的初始建议为 0.01，可在 0–0.05 内调整，超过此范围重新评估容量与预算。此处是拟定默认值，未更改任何线上配置。

- 以业务 Run 为单轮抽样单位，以会话/明确窗口为多轮单位；按 tenant/project、Agent 配置与任务类型分层，保留纳入概率、策略版本、时间窗和去重标识。子 span 不重复计样本。
- 全量运行结果统计与抽样质量分开；硬信号全量汇入候选的结果不混入随机质量均值。只评分正常完成请求时，指标命名明确限定该子集。
- 报告 eligible、sampled、scored、error、missing 数量及适用分母；低于冻结的最小样本量显示「样本不足」，不触发均分下降结论。跨层聚合保留权重和分层结果，不只给总体均分。
- TaskCompletion 需要可解释的任务目标与有效输出/工具证据；Faithfulness 仅用于有实际检索上下文的场景；F4 使用完整相关会话。非适用条件在评分前确定，缺本应存在的证据记 error，不能记 not_applicable。
- 原生在线评分优先验证：当前 `EvalFlow: mlflow/genai/scorers/base.py` 的 start()/sampling 配置及服务端作业支持不等于任意 DeepEval scorer 可直接注册执行。选择由 Task 4.0 形成结论；缺口在 eval_platform/ 补齐，不在 Agent API 新建 Celery 裁判服务。
- 复用已校准裁判及现有调用适配；记录模型、提示词、版本与用量。同源模型偏差通过确定性事实和人审控制。生产秘密经服务端安全配置注入，不依赖开发者 home 中的资源文件。

启用前冻结每日请求/Token 上限、并发、单次超时、有限重试、积压上限和样本保留期；预算未知则不启用。推理、裁判、嵌入分别核算，费用不可得记 unknown。暂停巡检不影响业务 Run。

### 7. 大盘、告警与性能

复用 Prometheus/Grafana/Loki 和现有页面。故障、预期拒绝、客户取消、评分错误分别展示；用户反馈率报告分母与未反馈流量，不当作全体满意度。

Prometheus 使用有界类别标签；租户/项目细分通过受控数据查询，不把 message/trace/user ID 变成高基数标签。告警复用已配置 Contact Points，实际通道、版本与模板须验证，不承诺无需配置即可支持所有 IM。通知只含最小摘要和受权链接，不发送原文。

Task 1.0 先测采集关闭时的吞吐、P50/P95/P99、CPU/内存和落库开销，冻结允许增量、最大延迟与可接受丢失条件；相同负载下复测。以证据验收，不承诺延迟增量 0ms、零成本或全故障检出率。
