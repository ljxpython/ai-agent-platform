## 这次要把使用流程改成什么样

你发现Agent算错、漏步骤，或者报告虽然没有明显错误但“不够好”。在原回答旁点**“让AI帮我改进”**，说明哪里不满意。也可以从项目的**“评测与改进”**入口直接提出一个测试需求。

AI先整理出一张可读的建议卡：它认为问题是什么、准备怎样验证、应该得到什么结果、哪些地方还不能确定。你不需要填JSON、寻找实验编号、逐条编写标准答案。认可就点**“同意方案并验证”**；不认可就直接说“退款应该按发生月份算，再补一个拒绝写文件的情况”。AI生成新版本，明确展示改了什么，等你评审。

确认后，系统自动完成材料收录、固定题库版本和运行。结果仍在同一个工作项中：哪些通过、哪些失败、哪些无法判断、AI建议先改哪里，以及每项判断的依据。正常结果自动记录；只有需要新业务口径、真实操作审批或存在评判争议时，才进入“需要你决定”。

这套功能主要服务业务负责人、Agent开发者和测试人员。普通使用者只需反馈问题；业务负责人确认规则，开发者查看失败原因和比较结果。**它帮助团队发现和验证改进，不会自动训练模型、修改代码或部署生产。**

### 四个名词，读到这里就够用

| 页面用词 | 实际意思 |
|---|---|
| 改进工作项 | 围绕一个问题保存讨论、方案、测试版本和结果的记录；关闭页面后仍能找到 |
| 测试方案 | 输入什么、准备哪些文件、分几步执行、什么算正确，以及还不确定什么 |
| 固定题库版本 | 把已同意的测试题保存成不可随意修改的一版，保证下次比较用的是同一把尺子 |
| AI评审建议 | AI根据规则和证据给出的判断，保留理由和不足；不是独立人审或正确性保证 |

## 一条正常流程，具体发生什么

### 1. 描述问题，AI负责整理

入口是原回答的“让AI帮我改进”或项目内“新建改进”。填写一句话即可开始，例如：

> 这个销售分析没有扣退款。请帮我整理测试方法，检查数字、是否保留源文件，以及报告能不能解释原因。

AI先读取**已获准使用**的内容。没有资料授权时，只能依据用户主动提交且允许用于本次AI分析的合成说明起草；原回答只保留关联编号，不偷偷读取整段会话。界面先说明将交给哪个受管模型、哪些内容、用于什么；缺授权时直接展示“需要资料负责人授权”，不能先发送再补手续。

AI输出：问题摘要、事实依据、原因猜测、建议覆盖的几类测试、缺失信息。事实和猜测分开显示。例如“最终金额没有扣退款”必须有输入与计算证据；“可能没有读退款文件”只能标推测，除非工具记录支持。

系统按问题类型合并重复建议，默认提出一小组代表性测试，而不是生成几十条改写题让人逐条审批。每条写明覆盖的风险；删除重复题不会抹掉原反馈的关联。跨项目或不同资料授权批次不做正文混合聚类。

### 2. AI提出完整方案，你评审整组

建议卡默认展示：

- **目标和范围：** 测哪个Agent配置，使用哪些资料和授权，在哪个隔离环境执行。
- **准备的测试：** 每类测试的输入、步骤、关键文件、预期结果和为什么需要它。
- **判断方法：** 哪些由算式/文件/工具记录直接判断，哪些由AI依据业务标准判断。
- **需要你决定：** 缺失口径、敏感资料用途、未获准的操作；没有问题则明确写“无”。
- **执行影响：** 会创建哪些测试文件，是否包含预设或在线审批；不会把“评审方案”当成生产写入授权。

按钮只有三个主动作：**同意方案并验证、提出修改、暂不处理**。细节和高级JSON检查放在展开区，不作为普通使用者的必填表单。

已有资料授权且有评审/执行权限时，一次确认可启动后续工作。缺少权限时，按钮显示“提交给项目管理员”或“提交方案评审”，同一工作项转交；不会为了少一次点击而替使用者取得权限。

### 3. 不同意，就用自然语言修改

你说“金额按退款发生月份算，不要按订单月份算”。AI回复修改摘要，并展示旧方案与新方案的差异：口径、输入、期望金额、增加/删除的测试和授权变化。没有变化的内容折叠，不要求从头重读。

每次反馈只发起一次修订作业。AI可以先问影响结果的关键问题，也可以提出带标记的假设；**关键业务口径未确定的测试不能进入已批准版本**。用户可选择先运行其余已确定的用例，界面同时保留排除项及原因，不能显示为全范围通过。

批准绑定准确版本。方案内容一旦变化，新版本必须重新确认；旧版本、旧批准、旧结果仍能回看。用户也可直接修改可读字段，或选择只接受部分建议；系统以最终选中的整组内容创建新版本。

### 4. 确认以后，系统自动固定版本并运行

后台依次检查当前身份与资料权限、校验测试结构与可执行性、记录评审、固定版本、创建运行。页面显示“准备测试→正在运行→正在分析→已完成”，不要求用户去另一个系统再点一遍“发送/审核/发布/启动”。

这是一个可恢复的作业，不是跨服务数据库事务。哪一步失败就显示具体原因，并从已确认成功的位置继续；例如题库已发布但运行创建失败，重试只补创建运行，不能再发一个题库版本。超时结果未知时先按请求编号查回执，不盲目重发。

每个工作项始终展示题库名称/版本、运行名称/状态和历史记录。刷新、关闭页面、重新登录后都能找回；从结果可回到对应方案和测试版本，不靠记实验编号。

### 5. AI解释结果，通常不再要求人逐条点通过

报告先给一句能行动的结论，例如：“6题中4题通过，1题退款月份算错，1题解释不够明确；数字错误建议优先修复。”随后展示失败证据、影响范围和建议，最后才是逐题明细。

明确规则优先：算错、越权写入、修改受保护文件不能被AI的高分抵消。缺少执行证据显示“无法判断”，取消显示“未完成”，不算全题通过。AI建议自动落档，**不把AI自己的‘很有信心’当成免审核依据**。

人无需逐条接受正常结果。对新业务口径、评分分歧或高风险操作，系统集中列出需要决定的事项。采用既定标准、证据完整且无冲突的主观评分可记录为“AI判定”，与确定规则的结果分列；不冒充专家校准结论。

### 6. 对结果有异议，先分清在改什么

| 你的反馈 | 系统如何处理 | 旧结果怎样保留 |
|---|---|---|
| “标准没错，但AI漏看了报告第二段” | 引用同一份证据，AI再核查并生成新的评审记录；必要时转人工裁决 | 原始运行、第一次AI判断和新判断并列 |
| “我们决定以后按退款发生月份算” | 改业务标准，创建新方案/评分版本；由有权人员批准后重评或重新执行 | 不改原用例，不把旧运行重新标成原标准下通过 |
| “这次失败先接受，不影响我们发布” | 单独记录接受风险的决定及理由；发布仍按外部发布权限处理 | 测试仍为失败，不能点一下变成通过 |
| “结果很好，以后都检查这组场景” | 将已发布版本加入本项目可重复运行的测试集合 | 不因此开启CI、定时抽样或新的资料用途 |

单次异议最多触发一次自动复核；再次不同意可以再提交理由，或者交人工决定。系统不能为了“达成一致”自行改标准、反复评分直到通过。这个限制只约束本专题的辅助作业，不代表实现了原暂缓的“停止Agent无效循环”。

## 复杂场景怎样处理

详细的可复制文件、对话和正确金额见[复杂场景走读](ai-workflow-scenarios.md)。主案例是“分析销售与退款，生成经营简报”，包含两次人对AI方案的修改，以及运行结果争议。

| 情况 | AI先做什么 | 人什么时候介入 |
|---|---|---|
| 多步骤任务 | 拆成读取资料、确定口径、计算、起草、审批写入；分别设计可观察结果 | 只确认业务口径与操作范围，不逐步批准读取和计算 |
| 多轮口径改变 | 保留对话顺序，检查后续回答是否记住最新要求；不能把多轮压成单轮 | 修改口径时看差异并批准新方案 |
| 需要工具审批 | 为回归生成“预设批准”和“预设拒绝”用例；确实需要现场判断时生成在线待办 | 在同一工作项看工具、准确文件路径和影响，批准/拒绝后续跑 |
| 结果不止一个正确写法 | 给出评价维度、合格/不合格例子和引用证据，允许多种措辞 | 先认可评价规则；有分歧再裁决，不逐句写标准答案 |
| 缺少资料 | 明确列出无法计算的部分，测试Agent会不会追问或编造 | 提供资料，或批准明确排除这部分，不能让AI猜造事实 |
| 需要别的同事判断 | 转交给当前项目有权限的成员，保留意见与版本 | 本期提供一次转交和一位最终负责人，不建立多人会签流程引擎 |

在线审批超时后停止等待并保留未完成结果；刷新不丢待办。任何审批绑定具体运行、工具调用、参数和版本，不能用“同意测试方案”代替任意后续写入批准。默认使用隔离合成资料和测试目录，未支持的外部业务工具明确显示“不支持”，不能假装执行。

## 页面怎么组织

平台项目导航新增一个**“评测与改进”**入口，沿用平台壳层、项目切换、表格、状态和详情组件。首页三个分区：**需要你决定、正在验证、验证结果**，可按Agent、提交者、状态搜索。草稿和暂不处理的工作项仍能通过“全部记录”找到。审批任务只展示给实际有权处理的用户。

打开工作项，顶部始终是问题名称、所属项目/Agent、当前状态和“下一步由谁做什么”；主体只有**问题与方案、运行与结果、历史记录**。右侧提供反馈输入和当前待办。ID、Trace、原生实验、JSON收进“技术详情”。没有权限和没有数据分别提示，不展示其他项目的名称或数量。

前端以服务端保存的工作项为准；离开页面不停止后台作业，刷新先读取已持久化状态。AI生成中展示当前阶段与取消按钮，生成失败保留上一版方案，不能清空用户反馈。窄屏按相同阅读顺序折叠，键盘可操作，状态不只靠颜色。

正常路径验收目标：在资料权限和执行配置已就绪的前提下，从提出问题到开始运行，**只需要一次方案确认**；无需跨系统登录、手填JSON或按用例逐条勾选。额外资料授权、重大口径修改、真实工具审批确有必要时，单独显示原因，不承诺所有场景都只有一次点击。

## 身份和资料使用：本方案需要批准的具体边界

### 使用平台现有账号，不增加一个“评测审核员”角色

`flywheel-reviewer`是本地验收曾使用的账号，不是平台新增的业务角色。目前EvalFlow依赖自己的原生登录和配置审核用户名；只把按钮换个名字不能实现平台身份统一。

建议：日常用户只登录Agent平台。Platform API验证当前用户、项目权限和资料权限，通过**仅供服务间调用的评测接口**访问EvalFlow。评审记录里的决策人是平台真实用户；后台服务身份只代表“执行了这个命令”，不能冒充人。EvalFlow原生界面保留给既有受权维护者，不要求普通用户再登录。

下表是本轮已实现的动作映射，只在启用本功能的环境生效。执行时还要满足资料授权、资源归属和原有Thread/Agent权限；平台超级管理员不能绕过项目成员关系。

| 动作 | project_admin | project_editor | project_executor |
|---|---|---|---|
| 提出问题、查看自己有权访问的工作项 | 可 | 可 | 可 |
| 维护测试方案、评审业务规则、固定版本 | 可 | 可 | 提建议，不能批准 |
| 运行已获准题库、取消自己发起的运行 | 可 | 可 | 可，仍需现有执行权限 |
| 取消项目内其他人的评测运行、指派评审负责人 | 可，留审计 | 不默认授予 | 不授予 |
| 设置AI使用政策、资料用途和有效期 | 可，但不能代替私有资料所有者同意 | 不授予 | 不授予 |
| 批准在线工具待办 | 可处理分配给自己的待办，仍受具体运行/工具权限限制 | 同左；不因此获得任意运行管理权 | 不新增审批权 |
| 查看项目质量汇总 | 可，按获准范围 | 可，按获准范围 | 只看自己有权访问的结果，不新增项目聚合权 |

原代码只允许项目管理员导出自己会话的合成复现。本方案不默默放宽成“管理员读全项目私聊”：普通成员可以提交独立合成测试说明；引用受限会话时仍需所有者现有权限及资料管理批准，未具备时保留关联编号并显示缺失条件。涉及扩大原会话外发范围的实现不包含在默认批准中。

### AI分析、重复测试、线上巡检是三个不同用途

本轮增加`evaluation_assistance`用途，用于生成方案、修订和解释结果；`regression`继续用于固定测试与重新执行；`quality_inspection`继续是线上抽查的独立授权。一个页面可展示并提交多个用途，但后台分别保存授权，不能把勾选其中一个等同全部批准。

每个用途限定项目/Agent、允许字段、受管模型路由、有效期、保留规则和操作范围。默认只处理主动提交的合成说明、合成文件及已获准的派生结果；工具原文、检索正文、整段真实会话不默认外发。只在既有有效授权范围内免重复确认，新增用途或扩展字段需资料管理者批准。

AI方案、修订历史、结果解释、缓存和衍生测试都保留来源授权关联。派生物不能比来源活得更久；涉及多个授权时取权限交集和最早到期时间。本期不混合不同授权批次的题库/内容，避免撤一批资料影响不清。

更改合成测试内容后，原已固定材料的授权不能自动套用：若项目政策已明确允许在相同字段/模型/用途内修订合成内容，由服务端生成新的内容绑定授权回执；否则同屏补批新的材料授权。禁止改写原授权的内容摘要。

### 简化审核，必须同时替换旧的校验入口

现有`Curation.approve()`要求原生审核队列完成，且`completed_by`与审核用户名一致。新路径不能让共享服务账号伪造这个条件。建议新增**平台评审凭证路径**，记录用户、项目、方案版本与内容摘要、决定、授权、时间和请求编号；EvalFlow验证后，作为明确的新评审方式收录。旧原生审核路径继续按旧规则工作。

平台签发的短时命令凭证限定接收方、操作、项目、工作项、内容摘要、过期时间和唯一请求编号；身份与权限由Platform API构造，浏览器不能传一个user_id当证明。EvalFlow回查当前授权，重放请求只返回同一回执；相同编号不同内容拒绝。私有接口不能通过原生Basic账号或公网任意访问。

新批次的原生实验默认不向普通原生账号开放，服务端受管读取后返回平台。所有Dataset/Run/Trace/产物和搜索路径都必须保留批次守卫。**不能只保护新页面、却通过原生链接绕过当前撤权或项目边界。** 完整跨平台SSO、旧账号迁移和角色清理后续另做；本期不删除旧账号、不篡改旧审核者。

## 实现边界与可复用模块

### 由谁负责什么

**2026-11-14用户已确认：评测助手放在平台Runtime；评测业务与证据留在EvalFlow；界面和权限分别由平台Web/API负责。** 此决定替代初稿中“在EvalFlow运行AI建议作业”的设计，业务目标及原12项覆盖不变。

| 角色 | 工作内容 | 所属层 |
|---|---|---|
| 评测助手Agent | 理解问题、查询获准证据、设计/修订测试方案、解释结果 | 平台Runtime业务Agent层 |
| 被测Agent | 真正执行经营分析、文件读写等业务任务 | 平台Runtime，独立Thread/Run |
| 评测执行器与评分器 | 准备测试、调用被测Agent、确定性断言、语义评分、保存结果 | EvalFlow的`eval_platform/`业务扩展层 |

```text
平台前端：提出问题、评审方案、处理待办、查看结果
    ↓ 当前平台登录
Platform API：身份、项目权限、资料用途、受限调用、真实用户审计
    ├─ 辅助分析 → Runtime评测助手：理解、取证、生成、校验
    │                 └─ 经平台受控接口读取获准的EvalFlow资料
    └─ 业务命令 → EvalFlow：工作项、方案版本、批准、题库、任务、评分
                      └─ 经Platform API网关 → Runtime被测Agent
运行完成：EvalFlow保存结果 → 经平台授权 → 评测助手解释 → 页面展示
```

评测助手的模型连接使用Runtime已有受管装配，本地合成验证优先使用用户已授权的xiaok DeepSeek；新Agent不自行读取另一套密钥文件。已有语义评分继续使用EvalFlow裁判客户端，不为统一名称搬动评分引擎。平台API负责授权和协调，不在HTTP处理函数里实现Agent推理循环。

助手与被测Agent可以使用同一个模型，但必须隔离Thread、Run、工具集和上下文。测试输入可以给被测Agent，预期答案、评分标准、助手讨论、历史评分和内部评审意见不能混入被测输入。共享模型不构成独立盲测；原暂缓边界保持。

### 技术栈与选择理由（已确认）

| 部分 | 采用技术 | 本次用途 |
|---|---|---|
| 工作台 | 现有Vue 3、TypeScript、平台组件 | 方案卡、差异、审批、结果和历史 |
| 平台业务接口 | 现有Python、FastAPI | 认证、项目权限、资料授权、审计及服务协调 |
| 评测助手流程 | Python、LangGraph `StateGraph` | 明确组织理解、读取证据、推理、工具调用和输出校验 |
| 模型与工具 | Runtime既有LangChain及受管模型/工具装配 | 复用模型目录、权限、用量、取消与运行约束 |
| 结构化输出 | Pydantic | 校验建议、版本依据、测试内容、差异和结果解释 |
| 真实回归与评分 | 现有EvalFlow执行器、确定性检查、DeepEval评分能力 | 保持执行和评分语义，保留可核查证据 |
| 运行与持久化 | 平台既有Runtime/GraphHarbor运行底座；EvalFlow业务存储与MLflow记录 | 各自保存运行事实、业务版本和评测证据，不新建通用队列或checkpoint引擎 |

使用仓库当前锁定依赖，本方案不要求升级框架。首期采用一个专用助手，不拆规划/审核/总结等多个自主Agent，不采用完整DeepAgents能力集。当前只需要有限业务工具和明确步骤，不默认开放shell、任意文件操作、Skills加载或子Agent委派。

原EvalFlow `TaskStore.reconcile()`在Worker退出后会标记执行错误，不能把现有任务持久化等同Agent跨进程恢复。平台已有Agent装配和运行底座，因此将助手放在Runtime；接入仍须验证持久化、恢复、取消与权限，不能照搬示例里的内存checkpointer。具体开发沿用[Runtime Agent开发指南](../../../apps/runtime-service/docs/standards/runtime-agent-development-guide.md)。

### 评测助手一轮怎样工作

```text
理解本次意图（新建方案 / 修改 / 解释 / 复核）
    → 读取当前获准的资料和方案版本
    → 按需查询证据、计算预期、检查用例
    → 生成结构化建议及变化说明
    → 程序校验结构、业务规则与当前权限
    → 返回可评审建议，结束本轮助手Run
```

模型可以选择有限工具，决定还需哪段证据、缺哪些信息、应补什么测试。工具仅执行受限查询、确定计算和用例校验；Runtime凭受信上下文经平台接口访问EvalFlow，不直连数据库，不持有任意MLflow管理员权限。发布题库、改变授权、确认方案和启动评测由有权用户触发后端业务命令，不交给模型自行批准。

例如用户说“退款按发生月份算，再加一个拒绝写文件的测试”：助手读取当前方案，计算金额，生成新用例和差异；后端确认来源仍有效、base_revision未变化后，在EvalFlow保存新草稿。助手返回旧版本或重复回执时不覆盖当前版本，也不能直接改已经发布的题库。

### 状态的唯一负责方

| 信息 | 唯一事实来源 | 另一端怎样使用 |
|---|---|---|
| 助手Thread/Run、节点进度、checkpoint与恢复 | 平台Runtime/GraphHarbor运行底座 | 工作项只保存引用及投影，不另实现助手运行状态机 |
| 方案版本、批准、题库版本、评测任务与结果 | EvalFlow业务层及MLflow记录 | 助手按当前授权读取；不能用聊天记忆替代正式版本 |
| 身份、成员关系、资料用途与权限、平台审计 | Platform API | Runtime/EvalFlow在执行边界验证，不信任模型或浏览器填写的身份 |

“等待方案确认”是业务状态：建议生成后助手Run结束，工作项保留待确认状态。用户几天后反馈，再启动修订Run并读取当前正式版本；无需让助手进程一直等待。被测Agent在执行中遇到写工具审批，才使用该运行的interrupt/resume；方案批准不能代替工具批准。

checkpoint恢复可能重新执行节点，因此发布、创建任务和工具续跑仍需幂等与回执核对。业务版本、审批依据和执行副作用不能只放在graph state中。助手运行中读取的材料、checkpoint和追踪副本同样属于授权派生资料，必须接入撤权、到期和清理，不能因为换到Runtime而遗漏。

### 最少新增记录

工作项及方案、评审、执行关联集中保存在EvalFlow扩展持久存储中，复用现有存储/锁/写入习惯；资料授权与平台审计仍由Platform API持有。不要两边各造一套题库或运行事实表。

| 记录 | 必须保存的信息与作用 |
|---|---|
| 工作项 | 项目、发起人、问题摘要、获准来源引用、Agent配置、当前方案、待办负责人；提供稳定找回入口 |
| 不可变方案版本 | 版本/父版本、测试内容及摘要、期望与证据、评价标准、变更说明、来源授权、AI模型/提示版本；解释“这次同意的到底是什么” |
| 决策记录 | 真实决策人、human/ai来源、动作/理由、被评版本/摘要、当前授权、时间；AI建议和人工批准分开 |
| 作业与执行关联 | 业务阶段、幂等键、回执、输入版本/摘要、题库版本、助手Thread/Run及评测Task/Run引用、取消与错误投影；不复制助手checkpoint或评测结果 |
| 在线待办 | 运行/工具调用编号、准确参数摘要、允许处理者、期限、决定和续跑回执；防止旧审批批准新工具调用 |

工作项显示状态由这些事实计算，不复制一个能与原任务冲突的运行状态。最短过程是“整理中→待你确认→准备测试→正在运行→正在分析→已完成”；另有“待补资料、等待工具审批、取消中、已取消、无法完成、资料已失效”。测试失败属于已完成的质量结果，不等于系统执行错误；资料失效优先封闭内容。

### 复杂测试格式与暂停恢复

现有Case v1/v2继续按原语义读取。新增v3表达每轮预期、已确认的业务口径、主观评价标准及版本，以及`preset`（预设）/`live`（在线）的审批模式。旧版`approve/reject`转换为预设模式，不能因为升级就变成等待人操作。AI建议先经过结构和能力校验：不支持的工具、缺失的业务规则、不可定位的文件和没有依据的预期进入待补充状态，不进入可发布集合。

被测Agent的在线审批不只保存在EvalFlow Worker内存。Runtime运行底座持有真实中断/checkpoint；EvalFlow持久保存Case/轮次、thread/run/interrupt引用、参数摘要、已完成证据和编排位置，等待时不占用模型调用。收到批准命令后先核对当前Runtime中断与本地关联，再从该位置resume；重启不能从第一轮重新执行。在线待办默认有效期30分钟，且不超过资料授权/运行的剩余有效期；到期后取消在途运行并展示未完成，不默认为同意。该默认值已随D5批准。

发起人、评审人、执行服务主体分别记录。原资料所属项目与隔离执行项目也分别绑定，创建运行前检查两端授权，不接受前端随意替换执行项目或Profile。平台命令凭证使用既有安全模块的签名与校验方式，专用接收方和操作范围；不能拿Runtime委托凭证直接调用任意EvalFlow接口。

### 工作项接口与一致性规则

平台路径前缀为`/api/evaluation/work-items`；沿用现有项目上下文、错误格式、审计及请求追踪，不另建登录。下表描述行为，具体命令字段以`modules/evaluation/workbench.py`及EvalFlow `work_items.py`的请求模型为准。

| 动作 | 请求关键信息 | 返回及校验 |
|---|---|---|
| 创建 / 查询工作项 | 问题、获准来源引用、Agent配置；查询支持分页/筛选 | 稳定work_item_id、可读状态、当前可执行动作；关联编号不代表读取权限 |
| 提交修改 | work_item_id、base_revision、反馈、request_id | 修订作业编号；旧版本并发修改返回冲突，不能覆盖另一人的反馈 |
| 批准并验证 | revision、content_hash、selected_case_ids、执行配置、request_id | 单一operation_id，逐阶段回执；部分选择先形成准确的新快照 |
| 提交结果异议 | run_id、judgment_revision、异议类型、理由/证据引用 | 新复核作业或待批准新方案；不覆写原Run |
| 处理工具待办 | pending_action_id、参数摘要、approve/reject、request_id | 接受/拒绝及续跑回执；校验当前处理者、版本、期限和授权 |
| 取消 / 撤销资料授权 | operation_id或grant_id、当前版本、request_id | 取消中/实际停止回执，或立即拒绝访问；取消不自动撤权，撤权触发取消 |

发布与运行关联以`work_item_id + revision + content_hash + execution_config_hash + request_id`去重；用户明确“再运行一次”产生新请求编号。以数据库/存储锁保证审批竞争只有一个有效结果，后到者看到已处理结果，不能二次resume。

### AI可以做什么，不能做什么

辅助AI只获得本次所需的、已校验权限的材料快照，以及固定的读取证据、计算合成数据、校验用例和提交建议工具。不能开放任意SQL、shell、文件路径、URL或生产操作。模型输出按结构校验、字段白名单和文件沙箱再次检查；模型不能签发授权、批准自己的新业务规则或直接发布题库。

来源文本、文件单元格、检索结果中的“忽略规则/读取别的项目”等内容只当数据。权限过滤必须发生在模型看到内容之前，不指望提示词保密。计算预期优先由确定程序核算，主观规则注明来源/假设，不把被测Agent的答案反推为标准答案。

每次生成/修订/复核只启动一个有界助手Run，内部可按需进行有限次模型/工具调用，沿用Runtime的超时、输入、输出和工具调用保护；结构错误最多允许一次受控修复，失败后提示用户，不无限自我修订。用户未设费用上限不等于作业无限循环，也不能把应用限制冒充网关硬上限证明。人工发起的合成验证可推进，缺网关说明的真实自动抽样继续关闭。

### 失败、撤权和回退

- 在模型读取、发布、创建运行、工具续跑和展示结果前复查当前权限。撤权后禁止新调用/新读取，清除页面和缓存中的正文；已发出的模型请求不能假称“收回”，应丢弃迟到结果并记录处理边界。
- 同一来源的方案、意见、解释、用例、产物，以及助手Thread/checkpoint、缓存、追踪中的内容副本一起纳入保留/清理/恢复机制，建立跨两仓的授权关联。延续合成资料不超过授权且最多30天、撤权立即封闭、在线副本24小时内清理、隔离备份/恢复副本最多7天、无正文最小审计90天的已批边界；外部模型服务保留策略不以本地清理冒充。
- 工作进程重启按持久回执恢复。执行结果未知先对账；不重放未知状态的写工具，也不自动重跑整个Agent。模型超时、资料失效、缺证据、规则失败和主动取消分别展示。
- 新增入口使用默认关闭的工作台开关。回退时先停止接收新作业，取消/排空在途作业并核对回执；保留已有版本和结果，不回滚资料撤权，不删除原题库。
- 用户旧题库、原实验8和历史运行保留原归属与审核身份；先只读关联到工作台，不搬数据。无法证明当前访问权的历史条目不展示正文，不能以“导入历史”为由补造授权。
