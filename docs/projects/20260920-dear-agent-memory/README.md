## 当前结论

**2026-09-22 范围澄清：** 用户明确只需要“项目内个人记忆”：同用户同项目可跨会话使用，不跨用户、不跨项目。项目共享记忆与跨项目记忆的存储/召回本期 deferred，未来另行考虑；不因权限专项而自动增加此类任务。当前权限专项只完成平台权限和个人记忆入口治理，本记忆专项的无线程接口、提取/召回优化等方案仍维持原有待评审状态；此次澄清不等于批准全部实施或修改 Runtime。

memory不是纯前端架子：已有页面CRUD、Platform授权代理、Runtime PostgreSQL持久化、自动候选和上下文注入。缺口集中在会话入口与个人项目作用域不一致、来源/状态不完整、错误包与前端读取错配、竞态、生命周期和召回质量。

本轮新增核查确认：Platform标准错误包是`error.code`，当前页面读顶层`code`；新委托operation在Platform和Runtime均有白名单，必须双端修改；队列消息需要确认真实作者，不能把其他参与者偏好写入run owner的个人记忆。

推荐保留人工采纳、三元scope、Runtime唯一存储、CAS/epoch。借鉴deer-flow来源与文件交互、过滤与预算，但不复制多后端、全局共享、自动批准和进程内Timer。

## 2026-09-24 用户确认记录

确认来源：用户在本次对话明确确认以下规则，后续实施与交接据此执行，无需重复确认这些取舍。

1. 沿用当前权限系统，用户仅管理本人在当前项目中的记忆；不新增角色、管理员代管或共享记忆。项目读取权限为 `project.runtime.read`，写入沿用当前 `project.runtime.execute`，服务端委托绑定真实用户。
2. 我们负责 Platform API、Runtime、后端验证及交接材料；前端由用户同事实施，本任务不开发前端。
3. 共享会话关闭个人记忆自动注入、全部记忆工具访问和自动提取。私有会话之后被分享时，分享包含历史回答，不能保证已经生成到回答中的个人信息仍然隔离。
4. 当前 run 内最多两次模型尝试，失败显示状态；不承诺跨 run 自动补偿，不建立后台恢复队列。
5. 自动召回存储故障时不注入记忆，记录降级，普通对话继续；显式管理和查询返回错误，不伪装为空库或成功。
6. 接受 run 内提取延迟最终完成状态；两次尝试共用最多 **180秒模型预算**，不是每次180秒，也不是整个 run 的总时限。

尚需收口的工程约束：共享状态如何经受信链路传入Runtime以及运行中分享的生效边界；并发run的状态归属与取消/提交竞态；摘要前来源捕获实证；容量重置后的去重语义。以上不代表用户尚未确认上述产品规则，也不扩大前端开发范围。

## 其他方案约束

1. 采用无线程的项目内个人记忆入口，保留旧入口至前端迁移完成。
2. 采用03的MemoryView，明确ready与disabled/null、标准error.code、action字段和导入计数。
3. 候选始终人工采纳；有界run内提取/有限重试，独立后台持久恢复不在首期。
4. Runtime PG唯一事实源；容量维护不阻止用户人工删除，自动提取耗尽时明确暂停。
5. 有界词法召回先通过固定样例集再冻结参数；画像/向量库/全局偏好另行评估。
6. 前端由其他同事完成；我们必须提供真实OpenAPI、请求响应、测试环境及后端验证报告后才能标“可交接”。
