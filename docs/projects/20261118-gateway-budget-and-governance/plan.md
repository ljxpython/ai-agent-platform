# AI 网关预算控制与财务熔断架构方案

> **状态：** 部分完成（partial）。2026-11-18 用户追加实施授权，已在独立 Worktree 开发；实际完成与未覆盖条件以 tasks.md 和 verification.md 为准。
> **范围：** 保留 GLOBAL / PROJECT、USD、日 / 周 / 月、ALERT / REJECT、超额通知和用量中心 Budgets 页。

## 1. 用户如何使用

管理员为当前租户或某个项目设置周期预算。用户正常运行智能体，用量中心显示本周期已记录的模型费用和重置时间。累计达到额度时，两种策略都会产生首次超额通知；ALERT 允许继续调用，REJECT 阻止之后新增的模型调用。调高额度后，后续调用可按新额度重新判断。

同一个长 Run 可能包含主 Agent、子 Agent、摘要、重试和备用模型等多次调用。因此预算必须在 Runtime 每次真实模型调用前检查，结束后逐笔记账，不能只在创建 Run 时检查、整个 Run 结束后结算。

本期按已结算费用判断准入，不预占资金，不承诺严格支出上限。已获准的并发在途调用可以完成并产生超支；这部分费用必须完整入账。继续保留现有单 Run Token、轮次和执行时间防护，两类预算分别生效。

## 2. 产品范围与边界

| 维度 | 本期规则 |
|---|---|
| 作用域 | GLOBAL 指当前 tenant 的所有项目，不是跨租户的平台总池；PROJECT 仅约束同 tenant 的指定项目。所有命中的 REJECT 策略都必须满足 |
| 金额 | 仅 USD，额度必须大于零；使用现有价格快照计算的估算费用，不作为供应商最终结算账单 |
| 周期 | 每日 UTC 00:00、每周日 UTC 00:00、每月 1 日 UTC 00:00，对齐自然周期，区间左闭右开 |
| 动作 | 已记录费用大于等于额度即超额；ALERT 通知并继续，REJECT 通知并阻止新增调用 |
| 界面 | 沿用用量中心 Gateway、Logs、Governance，增加 Budgets；保留策略创建、查询、编辑、删除和三色进度 |
| 非目标 | 不增加余额预占、多币种、充值支付、成本预测、自动切换便宜模型或 80% 外部预警。80% 仅为界面提醒 |

预算不阻止历史读取、查询状态、停止 / 取消或管理员修复策略等不新增模型费用的操作。实际产生模型调用的恢复、重试和后台执行仍需检查。

## 3. 当前事实与职责划分

### 3.1 可以复用的事实来源

- Runtime 的 [usage 采集](../../../apps/runtime-service/src/runtime_service/observability/usage.py) 和 [usage 仓储](../../../apps/runtime-service/src/runtime_service/db/repositories/usage.py) 已记录逐模型调用事实。费用字段是 `estimated_cost_usd`，价格保存在 `pricing_snapshot`。

- Platform API 的 [终态契约](../../../apps/platform-api/src/platform_api/modules/runtime_gateway/domain/completion.py) 不包含费用。不能假定存在网关财务日志库，也不向终态回调强塞整 Run 费用结算。
- 现有通知渠道可以复用，但 [进程内告警冷却](../../../apps/platform-api/src/platform_api/modules/notifications/alert_governance.py) 和 [通知派发](../../../apps/platform-api/src/platform_api/modules/notifications/service.py) 不提供本项目需要的跨进程持久幂等与可靠重试。

上述是复用的代码事实。2026-11-18 已在独立 Worktree 实现下文预算窗口、准入和预算事件，验证边界见 verification.md；不将可选 MLflow / Langfuse Trace、客户端回传或历史页面读取作为扣费权威。

### 3.2 服务边界

| 服务 | 负责什么 | 不承担什么 |
|---|---|---|
| platform-api | 策略持久化、权限与审计；向 Runtime 返回受信策略；聚合预算状态；接收并投递预算通知 | 不依赖 Run completion 计算费用，不直接读取 Runtime 数据库 |
| runtime-service | 每次真实模型调用前准入；逐调用费用落账；在同一 PostgreSQL 事务内更新派生窗口和预算事件；恢复与重建 | 不接受浏览器提供的预算身份、金额或跳过检查标志 |
| platform-web | Budgets 管理、费用 / 数据质量展示、受控拒绝提示和恢复指引 | 不自行计算权威余额，不用显示用浮点数判断后端是否应放行 |

Runtime PostgreSQL 是费用事实和预算派生状态的唯一记账边界。首期不引入 Redis 金额计数作为必要依赖，也不维护 Redis 与 PostgreSQL 两份财务权威。

## 4. 执行架构与策略生效

### 4.1 每次调用的处理顺序

1. Runtime 在模型调用封装处取得平台认证链路建立的 tenant / project 身份；主 Agent、子 Agent、已纳管辅助模型、异步恢复和实际重试尝试都走该入口。
2. 每次调用通过受认证的内部控制面查询解析适用策略，取得 tenant 策略集单调版本、策略版本和完整规则，包括必要的删除标记与定义生效边界。首期不使用跨调用的策略缓存，也不把策略冻结在整个 Run 上。
3. Runtime 在数据库短事务中取得租户事务锁，登记 / 核对窗口，完成必要回填，然后读取最新已提交费用与数据质量。命中超额 REJECT 则拒绝；账务不可核实则按第 6 节处理。
4. 放行时持久化调用开始标记、调用身份和价格快照，再提交事务；ALERT 也不能在开始记录无法持久化时发送模型请求。事务锁不跨越模型网络调用，不进行金额预占。
5. 调用完成、失败或取消后，将可获得的用量和费用事实、窗口差额及首次超额事件一并提交。受 REJECT 管控的后续调用不能绕过尚未确认的结算结果。
6. 持久事件由独立投递流程重试发送到 Platform API 通知服务。重放调用结算或重启 Worker 均不重复累计费用。

不能仅靠一个允许吞掉异常的观测 callback 实现硬限制。本轮使用同步dispatch guard在实际模型发送前中断，账本提交失败会影响后续准入；预算启用时关闭SDK隐式重试，显式尝试分别准入/记账。Task 3仍需补真实主备/异步恢复组合证据，不把未覆盖路径记为通过。

### 4.2 新策略、编辑与删除

- 策略管理响应表示控制面版本已提交。已取得受信策略快照的准入流程可按该快照完成；之后开始解析的调用读取新版本。所有调用均有受控超时，不无限期持有旧快照。
- 保存后由控制面主动请求 Runtime 应用规则，失败保留持久重试任务，响应明确显示待应用。每调用解析仍是准入正确性的保障；列表同步登记/回填当前自然周期窗口并读取状态，不凭历史页面读取制造调用费用。
- Runtime 记录已见的 tenant 策略集版本；晚到的旧响应不得覆盖新版本，需重新解析。空策略集也必须来自成功的受信查询；查询失败不等于没有预算。
- 同一 Run 的下一次模型调用重新解析，因此新增、调额、改动作、改周期和删除可影响长任务的后续调用。删除不撤销已发生费用或删除账务历史。
- 调整额度 / 动作只增加策略版本，不重置当前累计，也不重置本窗口已生成的超额事件。调低额度到已用金额以下时，策略应用事务即生成首次超额事件；调高后按新额度准入。
- 改变周期或作用域建立新的窗口定义版本，对新定义的当前周期回填已有已纳管调用；旧定义和其生效边界保留，接收边界前调用的迟到补记。不同定义的历史金额不相加成一个当前余额。
- 新建策略从本自然周期起点回填符合范围的已有调用，而非从零起算。缺失的历史价格或用量仍标记为不可核实，不能套用今天的价格伪造历史费用。

Platform API 可以在创建新 Run 前调用 Runtime 的同一权威检查服务，提前返回拒绝，节省初始化开销；它只是优化，不代替 Runtime 每调用检查。不得凭前端状态或本地过期缓存作硬拒绝依据。

## 5. 记账规则与一致性

### 5.1 数据与金额约束

除现有调用事实外，Runtime 已增加以下必要持久记录：

| 记录 | 必须保留的信息 |
|---|---|
| 预算窗口 `runtime_budget_windows` | tenant、策略 ID、窗口定义版本、起止时间、已确认金额、数据质量和核对时间；唯一键包含完整周期身份 |
| 调用计入记录 `runtime_budget_contributions` | 窗口身份、完整调用主键、已计入金额和来源状态；唯一约束防止同调用重复计入同窗口 |
| 预算事件 `runtime_budget_outbox` | 稳定事件 ID、窗口业务唯一键、触发时规则快照、已用金额、投递状态、重试和失败原因 |

`runtime_budget_tenants`保存已见策略版本，`runtime_budget_call_leases`保存调用租约，`runtime_budget_worker_fence`保存执行域门禁激活状态；这些持久信息同样参与重启恢复，不能跟随Thread或Trace清理。

计算使用 Decimal，持久化使用 `numeric(28,12)`。HTTP 金额统一为最多 12 位小数的十进制字符串；JSON 浮点、前端 Number 或 Redis Lua double 均不作为权威金额。计算精度、舍入方式和溢出校验沿用现有费用口径，并测试边界。

“本次增量 = 该调用最新可信费用 - 此窗口已计入该调用的费用”。重复消息增量为零；缺失 / 部分用量补为可信用量时只补差额。最终事实不因重放回退为缺失，不因当前模型改价而重新定价；不得覆盖调用主键或把整个 Run 总额重复加入。

失败、取消但供应商已产生费用的调用仍计入。未发送到模型的预算拒绝不计费；实际重试尝试使用不同调用身份，各计一次。同一事实重放沿用原身份。

### 5.2 周期归属与数据质量

费用按 `model_call_started_at`（账本 `started_at`）归属周期，整笔归开始周期。23:59 开始、次日结束的调用补记前一天窗口，不转入当天，也不覆盖前周期记录。当前窗口重置后，历史费用与告警仍可核查。

区分正常在途调用和结算异常：在途记录不预估为已花费，也不因尚未结束就禁止全部并发；检测到失联未闭合调用、已结束却缺用量 / 价格或结算失败时，将相关账务标记为不可核实。不能把未知当作零或把已知费用的局部和当成完整总额。

账本和计入记录的保留不得跟随 Thread 删除或 Trace 清理而减少有效预算。需核对现有删除 / 保留链路；不能保留重建所需事实时，不允许把派生状态标为完整。

### 5.3 多 Worker、回填与恢复

首期选择易于验证的 PostgreSQL 租户级事务栅栏：同 tenant 的所有调用事实写入、窗口初始化 / 重建和相关派生更新，必须在同一事务内先取得同一事务锁，再读取和修改数据。采用 READ COMMITTED，锁后重新读已提交状态；不复用锁前旧快照。

- 所有调用费用写入都遵守栅栏，包括尚无匹配策略的调用。新窗口在锁内登记并扫描已有事实；后续写入同时更新所有适用的已登记窗口，不能只看该调用开始时携带的旧策略。
- 事务内完成调用 upsert、按调用计算差额、更新窗口及写入 outbox；任一步失败全部回滚。跨项目 GLOBAL 与 PROJECT 同时命中时也不能只成功更新一部分。
- 回填与实时结算使用相同幂等计入记录和事务栅栏。先启动后晚提交的写入必须被扫描或由后续增量纳入，不能用自增序号充当事务提交顺序。
- 进程重启读取持久窗口。窗口丢失、算法变更或核对不一致时从调用事实重建，核对前保持 reconciling / unverifiable，不以临时零余额放行 REJECT。
- 回填同时核对用量采集覆盖和降级记录；存在无法证明完整的历史区段时保持不可核实，不能只对查得到的调用求和后宣称完整。
- 首次回填用有界扫描和超时保护；事务失败保留待恢复状态，不进入模型调用。大窗口的锁等待和回填时长纳入性能验收，不能声称无锁或固定低延迟。

本轮实现把已结束但缺少 Usage 采集记录的受信原生 Run 持久标为采集缺口；Thread 清理后该降级证据仍保留。不能从历史缺少记录推断费用为零，也不能推断未纳管时期的完整供应商账单。窗口累计与逐调用计入总额不符时，在持锁事务内从调用事实重建，失败不放行。普通只读 Usage 查询保留原超时；带租户栅栏的记账写入采用 2s statement / 1s lock，控制面回填采用 4s / 1s 有界超时。该调整来自本地 8 并发触发原 250ms 锁超时的实际测量，不构成生产容量承诺。

不跨外部请求持锁；多 Worker 准入与结算按提交顺序看到累计。锁串行化保证累计一致，不保证在途调用不会超支。只有性能证据证明首期栅栏不满足要求时，再单独评审更细粒度方案。

## 6. 故障处理与准入语义

| 条件 | ALERT | REJECT |
|---|---|---|
| 账务完整且未达额度 | 放行 | 放行 |
| 账务完整且达到额度 | 产生首次超额事件并继续 | 产生首次超额事件，拒绝新增调用 |
| 已知本次调用价格缺失，或窗口缺价格 / 用量、正在重建 | 可降级继续，显示不可核实并记录原因 | 停止新增调用，返回受控账务不可用原因 |
| 已有持久开始记录，但费用结算暂不能确认 | 有持久证据时可降级继续，但不能标记账务完整 | 停止新增调用，恢复并核对后再准入 |
| 数据库不可用，无法持久化新调用开始 | 返回受控不可用，不发送模型请求 | 返回受控不可用，不发送模型请求 |

已确认的部分金额已经达到额度时，也能确认超额；否则账务不完整只能判为不可核实。页面同时保留数据质量状态，不能以超额已知推断总额完整。

ALERT 降级仅适用于已成功确认所有命中规则均为 ALERT 的调用。控制面查询失败、身份无效或无法确认是否存在 REJECT 时，不得按空策略或 ALERT 放行。已确认无匹配策略则维持现有运行行为。

故障不抹掉已产生成果，不禁止读取和停止。故障恢复后，用持久调用事实核对补记；无法恢复的费用继续显示未知并进入人工处理，不能仅凭数据库恢复连接就清除不可核实状态。价格为明确零价与价格缺失必须区分。

## 7. 控制面 API、安全错误与通知

### 7.1 策略和状态接口

Worktree 已实现 `/api/policies/budgets` 的 GET / POST，以及 `/{policy_id}` 的 PUT / DELETE。写响应返回 policy 与 applied/pending；列表返回 items 与 revision。内部契约冻结为 POST `/api/runtime/internal/budgets/resolve`（Runtime→Platform）、POST `/internal/budgets/query`（Platform→Runtime，sync/status/check）和 POST `/api/runtime/internal/budgets/events`（Runtime→Platform）。完整前端字段见 frontend-handoff.md；不表示主环境或生产已部署。

- 策略管理必须按已认证 tenant 查询。GLOBAL 管理由平台管理员承担；PROJECT 管理按现有权限标准中的项目管理权限收口，普通成员不能改策略。GLOBAL 的“全局”不赋予跨租户访问权。
- 查看范围沿用用量中心权限。项目视图不返回其他项目费用，也不向无租户级权限的用户泄露 GLOBAL 聚合金额；必要时仅返回影响本次运行的受控原因。
- 内部接口验证现有服务认证 / 签名链路及该方向的适用性，绑定方法、路径、请求体、时效和身份，具备重放防护。不能假定已有反向签名接口或接受公网伪造来源。
- 创建 / 编辑金额使用字符串，例如 `"200.000000000000"`；周期仅支持 DAYS / WEEKS / MONTHS 且 value 为 1。校验精度、范围、scope 与 project_id 关系，记录审计与版本。
- 列表返回规则版本、`window_start`、`window_end`、`accounting_status`、`known_spend`、核对时间。只有完整状态下 `current_spend` 才返回完整金额；未知或恢复中为 null。已确认部分已超额时 `is_exceeded` 可为 true，否则不可核实状态为 null，不能以 false 假装安全。无权字段省略。
- 创建 / 编辑响应区分“策略已保存”和“当前窗口已就绪”。Runtime 尚未完成回填时显示恢复中，REJECT 按恢复中规则处理。

### 7.2 HTTP 与流式运行

流建立前已确认超额返回 HTTP 429，`Retry-After` 根据最早到期的相关窗口计算，恢复时间同时给出；其他命中策略仍可能继续阻止调用。账务不可核实返回受控 HTTP 503，不伪装成超额或认证失败。

复用 [build_error_payload](../../../apps/platform-api/src/platform_api/core/errors/payload.py) 和 [错误 Envelope 标准](../../standards/error-envelope.md)：使用 `error.code`、`error.message`、列表型 `error.details`、安全 `error.extra` 和根级 `request_id`。本轮已冻结以下错误码：

~~~json
{
  "request_id": "req-example",
  "error": {
    "code": "BUDGET_LIMIT_EXCEEDED",
    "message": "预算已用尽，后续模型调用已停止。",
    "details": [],
    "extra": {
      "resets_at": "2026-12-01T00:00:00Z"
    }
  }
}
~~~

本轮拒绝错误仅提供安全重置时间，不增加策略金额，避免泄露其他项目或 GLOBAL 聚合费用。账务不可用为 `BUDGET_ACCOUNTING_UNAVAILABLE`，返回可重试指引；不得泄露内部调用栈或提示词。

SSE 已建立后不能改写 HTTP 状态为 429 / 503。Runtime 应停止下一次模型调用，通过现有安全投影允许的执行错误 / 预算通知表达原因，并持久化可回读的停止原因；需扩展白名单时同步契约测试。不自造 Run 终态，不把预算拒绝自动重试或切换备用模型绕过。

### 7.3 首次超额与可靠通知

ALERT 和 REJECT 在每个窗口首次达到或超过额度时都生成超额事件，事件与记账事务一起提交。唯一业务键包含 tenant、策略、窗口定义版本、窗口起止和事件类型；额度 / 动作调整不重置该键，重新越线不再生成同窗口第二条首次事件。

Runtime outbox 重试投递到 Platform API。接收方按稳定事件 ID 幂等持久化通知与投递任务后才 ACK；Runtime 收到 ACK 再标已交付。站内信按事件 ID 去重，外部渠道记录重试和失败，可用事件 ID 供接收方去重。

保证数据库中首次事件唯一及至少一次投递尝试，不承诺外部接收端端到端 Exactly Once。发送成功但 ACK 丢失可能产生外部重复；进程内冷却不能替代持久 outbox。通知不参与模型调用热路径。

## 8. 前端交互

复用现有用量中心导航、表格、表单、权限与错误展示组件，新增 Budgets Tab，并按现有 URL query 约定恢复选中项。

## 9. 实施、性能与回退

1. 先完成双服务增量迁移、策略版本和受信契约，再实现 Runtime 账本事务与重建。迁移需可重复升级，账务表不做破坏性降级。
2. 覆盖全部实际模型调用路径后，再启用 REJECT。新代码通过 SQLAlchemy session capability 与 Runtime `runs` pending→running 数据库 trigger 实施粘性门禁；首次激活先排空 running Runs。门禁作用于整个 Runtime 执行域，包括无 PROJECT 预算的项目；同步/兼容检查可激活空策略集的执行门禁，旧 Worker 或关闭预算/Usage 的连接均不能领取。不能宣称新旧执行版本可透明混跑，具体步骤见 backend-runbook.md。
3. 完成前端、通知和跨服务演练。性能测量包括真实认证、策略查询、事务锁等待、逐调用写入、回填和现有费用采集的影响；不保留原先未经测量的“≤2ms”承诺。
4. 实施前登记基线、负载与当前 SLO；若无既定阈值，由人工确认可接受增量后判定性能结果。没有阈值或完整链路证据不能标性能通过。
5. 回退保留策略、费用、计入记录和 outbox。只读页面可退回；执行服务回退须保留预算检查与Worker门禁，或暂停整个受保护执行域的新任务。不能仅停有REJECT的项目后撤销全域栅栏。直接回退成可绕过预算的版本不是兼容回退。
6. 重启、故障恢复、兼容回退与再次升级必须核对金额、窗口、版本和告警历史；不得为了恢复可用性清空账务。真实联调前遵守 [Worktree 资源隔离规范](../../standards/worktree-development.md)。

具体任务与证据分别维护在 [tasks.md](tasks.md) 和 [verification.md](verification.md)，README 仅做摘要。
