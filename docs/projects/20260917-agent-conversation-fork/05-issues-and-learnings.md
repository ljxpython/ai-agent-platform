# 会话分支与运行体验测试开发全景复盘

## 概述
在会话分支（Conversation Fork）、工作区协同、工具调用策略及多模态图表渲染的联调测试过程中，前后端暴露并排查了一系列深层次交互与架构脱节问题。本文档归档记录所发现的全部关键缺陷、根本原因及排查结论。

---

## 1. 业务交互与用户体验缺陷

### 1.1 工作区刷新按钮失灵 & 全屏容器排版错乱
- **现象**：用户在右侧工作区面板点击“刷新”按钮无法重新拉取文件目录树；点击“全屏”按钮后，工作区尺寸异常挤压变形。
- **根因**：
  1. `WorkspacePanel.vue` 的刷新按钮未正确绑定触发刷新 composable 动作；
  2. 全屏状态下使用了固定绝对定位与外部弹性容器冲突，导致 DOM 计算高度为 0 或严重缩放。
- **状态**：已在前端修复绑定与自适应布局样式。

### 1.2 新建分支工作区物理文件丢失（开局为空）
- **现象**：原分支已生成多项文件（如 `sales.csv`、`report.py` 等），从原分支中间轮次新建分支后，新会话工作区没有任何文件。
- **根因**：原设计仅完成了 LangGraph 状态检查点的分叉，未考虑底层文件系统的沙箱隔离机制；`resolve_thread_workspace` 为每个新 `thread_id` 自动开辟独立的物理目录，缺少文件树深拷贝机制。
- **状态**：在 Runtime 服务引入 `/workspace/fork` 接口，在分支创建时由 API 网关同步触发工作区物理目录树递归克隆，实现物理隔离与历史文件继承。

### 1.3 新建分支内容严重污染（带入后续轮次）
- **现象**：在多轮会话（如第 1 轮、第 2 轮、第 3 轮）中，从第 2 轮点击“新建分支”，新分支不仅包含了第 2 轮，还把第 3 轮的问题和回答一起复制到了新分支。
- **根因**：
  1. 前端获取 checkpoint 算法过于简陋，使用了单向 `some(m => m.id === targetId)` 判定，匹配到了最新的检查点；
  2. 在早期轮次查找未命中时，错误降级使用了当前会话最新的 `currentState.checkpoint`。
- **状态**：设计并落地了严格排他性检查点匹配算法（`findExclusiveCheckpointForMessage`），严禁包含下一轮任何消息；并在前端引入了检查点分页历史循环回溯拉取。

### 1.4 新建分支读取会话失败 (500)
- **现象**：点击分支后直接弹出错误弹窗：“读取会话失败 (500)”。
- **根因**：子会话创建时，网关未显式落定父会话的 `access_policy`，子会话以缺失策略状态访问 Runtime 网关，被安全校验拦截并抛出未捕获异常。
- **状态**：在网关 `create_thread` 流程中强化元数据继承，确保 `access_policy` 严格透传。

### 1.5 递归死循环保护阈值触顶 (Tool call limit reached: 49/48 calls)
- **现象**：智能体执行复杂多步骤规划和深度分析时，抛出 `Tool call limit reached: thread limit exceeded (49/48 calls)` 强行中断。
- **根因**：DearFlow Agent 在 `agent.py` 中写死了单线程最多 48 次工具调用的硬上限。
- **状态**：将调用限制提取为通用环境变量配置（`DEARFLOW_MAX_TOOL_CALLS`），调整至合理安全数值并写入 `.env` 与系统配置说明。

### 1.6 全权负责策略下仍弹窗人工审批
- **现象**：用户在顶部已选择“全权负责 (Full access)”模式，执行 `present_artifacts` 或 `write_file` 时前端依然弹出人工确认对话框。
- **根因**：前端 `approvals.ts` 的自动放行规则只涵盖了部分工具，对标准产物工具依然判定为高危敏感操作。
- **状态**：已在 `approvals.ts` 中规范化 full_access 的无感静默执行白名单。

## 2. 产物交付与图表渲染架构断层

### 2.1 产物路径白名单与契约脱节
- **现象**：智能体通过 `present_artifacts` 发布生成的架构图或流程图后，文档中显示碎图（404 裂开），且工具卡片未展示图表。
- **根因**：
  1. 产物规范升级：标准交付物统一收敛至 `/workspace/outputs/{sha256}.png`；
  2. 权限与正则硬编码脱节：后端网关（`service.py`）、运行时（`image_refs.py`）、前端校验（`images.service.ts`）与前端正则（`transcript.ts`）全部硬编码为 `(?:charts|generated|uploads)`，全面遗漏了 `outputs` 目录，导致合法产物被各层判定为非法路径。
- **状态**：已查明根因并记录契约规范，待全链路受控对齐。

### 2.2 工具卡片（ToolResult）数据抽取不匹配
- **现象**：`present_artifacts` 返回了结构化媒体信息，但卡片下方未渲染大图。
- **根因**：`ToolResult.vue` 仅提取 `props.tool.artifact`，而 DearFlow 标准产物输出保存在 `props.tool.output`；对非字符串类型的 `output` 未做结构化对象兼容，导致引用提取为空。

### 2.3 Markdown 原生图片标签与浏览器 404
- **现象**：模型在 Markdown 中输出 `![总体架构](/workspace/outputs/xxx.png)`，文档中该位置图片破裂。
- **根因**：`markdown-it` 默认将其渲染为 `<img src="/workspace/outputs/xxx.png">`，浏览器直接向前端 Vite 开发服务器（`localhost:5173`）发起未携带 Token 和 Project 作用域的相对路径请求，导致 404 裂图。

### 2.4 正文图文分离与排版倒错经验教训
- **现象**：若简单粗暴地在 markdown 渲染阶段将 `/workspace/` 路径图片置空，并依赖 transcript 在消息尾部统一追加 `<ThreadImage>`，会导致正文原本出现图片的地方空缺，而图片被排到整条消息的最末尾（在后续总结段落之后）。
- **改进方案**：
  必须采用**原地切块（Split by Image Block）**机制，将一段混有 Markdown 图片的文本切解为有序序列：
  `[前半段 Markdown] -> [原位 ThreadImage 媒体块] -> [后半段 Markdown]`，确保视觉排版与文本语义 100% 贴合，绝不跑到消息末尾。
