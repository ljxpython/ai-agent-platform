# 05 — 旧功能直接退役与新版切换

## 目标

按用户批准，实验阶段不维护旧项目。旧工具策略、Agent 工具选择和旧执行状态直接退役，不转换、不兼容、不保全旧行为。本专题保留新功能必需的数据库结构更新与单版本切换，文件名沿用现有链接。

## 方案设计

### 1. 取消的工作

- 不导出/映射旧 project_tool_policies false、排序或备注到新系统。
- 不盘点并保全旧 Agent.context.tools 的空列表或选择子集，不创建对应 Agent 变体。
- 不开发 migrate_runtime_tool_governance.py、dry-run/apply 业务迁移或转换测试。
- 不转换旧 JWT、Context hash、snapshot、checkpoint、草稿、排队任务或审批状态。
- 不要求旧历史可读、旧会话继续或旧功能回滚恢复作为交付门槛。
- 不做双读双写、兼容开关或旧授权兜底。

以上范围只针对本专项退役的工具功能；不意味着删除无关项目、用户、模型、工作区或其他专项数据。

### 2. 新功能与数据库结构

- runtime_tool_restrictions 空初始化，新禁用例外由管理员在新界面配置；默认无额外拒绝仍受 Agent 声明、scope 与资源校验约束。
- 通过正常 Alembic schema revision 创建新表、移除旧工具策略表及相关外键；不转换旧策略行。业务数据迁移取消不等于新表可以不建。
- 旧 Agent/线程配置不做运行期兼容；需要使用新版时重新创建符合新契约的配置和会话。旧 tools 字段请求明确拒绝。
- 旧接口、ORM、服务、前端开关与测试夹具一并退役，代码只实现新版。
- 当前另有 PostgreSQL 专项，实施前只核对届时实际 schema head 与连接配置，避免 revision 冲突；不修改或推翻其他专项的数据保全要求。

### 3. 切换顺序

1. 完成新版代码与测试，核对 Web、Platform API、Runtime API/Worker 使用同一契约版本。
2. 停止旧运行入口与旧 Worker；旧任务、审批和终端不要求延续，确保不会在新版后台继续执行。
3. 执行本专项 schema 更新，启动新版服务；不重建无关业务表。
4. 使用新 Agent 配置、新会话和新权限记录验收：普通聊天、false 拒绝、目录无关性、直接 HTTP、MCP/子 Agent 与审批。
5. 刷新展示目录与浏览器资源；旧客户端/旧 token 明确失败，不自动翻译请求。
6. 记录版本、实际变更和新功能验收结果。

切换失败时停止新版入口/Worker，修复后重试；不为恢复旧工具功能增加代码或数据恢复流程。新系统已经产生的数据与外部副作用仍须按真实情况处理，不能因“旧数据不保留”而忽略新功能的数据安全。
