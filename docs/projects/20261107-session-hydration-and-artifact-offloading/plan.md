# 会话快照水合与媒体外置治理 - 整体方案

> 修订：2026-11-07。总体方向已获用户确认；仅覆盖新会话、新数据，GraphHarbor 保持通用 Agent Server 边界。SDK 锁定包、事件回放和 Runtime 工具事件时序已完成初步核查。本文取代初稿中的存量兼容、固定体积和“50ms 秒开”承诺。

## 一、问题与证据边界

初稿记录了生产会话打开缓慢、步骤逐批出现，以及单次响应 5,702,925 字节的观察。该会话只作为问题背景，不作为本期修复对象或验收夹具。

初稿未提供可复核的 HAR、性能 trace 和响应字段体积分布链接。现有 `apps/platform-web/scripts/inspect-session-loading.mjs` 在 response 回调记录时间、只读取 Content-Length、按 URL 首次匹配请求并每秒采样 DOM；这不足以单独证明完整下载耗时、JSON 解析阻塞时间或毫秒级渲染收益。原“证据已沉淀完成”改为待补采，使用隔离环境新建夹具。

## 二、范围与不做事项

### 本期覆盖

- 新版本上线后新建会话中的工具媒体结果及其引用；以本期版本实际启用的图片、文件等媒体能力为范围，不新增媒体种类能力。
- 上述会话的首次打开、刷新、缓存切换、活跃运行重连、完成后再打开、继续提问、审批、停止、分支与子任务查看。
- 新引用的持久化、模型消费、经鉴权的预览/下载，以及会话生命周期内的留存和回收。

### 明确排除

- 上线前已有会话及其后续续聊的兼容、修复、迁移、回填和性能治理。
- 旧消息格式 fallback、双读双写、旧客户端/旧 Runtime 读取新引用、版本回退兼容代码和专用兼容测试。
- 新对象存储服务、历史数据批量改写、数据库迁移、无关重构或依赖大升级。
- GraphHarbor 的业务耦合、平台媒体处理、业务快照接口或业务数据库字段；当前验证没有发现必须修改 GraphHarbor 的缺口。

验收环境使用新建会话；无须为区分新旧会话新增版本路由或判断分支。不处理存量不等于删除存量数据，也不等于取消新功能的失败保护。基础模型协议适配、网络故障恢复和权限校验属于本期功能正确性，不是旧逻辑兼容。

## 三、设计与服务责任

### 3.1 媒体先落盘，消息保存引用

工具结果在进入持久化消息前，按当前支持的结构化媒体类型识别内联二进制，不依据字符串长度猜测 Base64。对识别到的内联二进制统一引用化，不保留按 64KB 阈值切换两种持久化格式的分支；普通文本继续使用现有输出预算机制。

处理顺序：

1. 复用 Workspace 的路径边界、类型/大小校验及远端路由，保存不可变媒体快照；源文件之后被覆盖，不改变已保存消息的含义。
2. 文件保存成功后，返回含最少引用信息的标准消息；保留 message ID、tool_call_id、工具状态及非媒体内容。
3. 引用携带可定位的受控路径/标识、MIME、大小及校验摘要等必要信息，具体字段复用已有 FileRef/图片引用/ArtifactRef，T02 冻结一个本期契约；不另造 UUID 成果物体系。
4. 保存失败则返回明确失败，不发布悬空引用、不悄悄退回内联 Base64，也不重新执行已产生副作用的工具。
5. 重复读取相同内容复用不可变数据；主图与子图使用同一规则。

必须验证两条实际出口：checkpoint 中的消息，以及公开 SSE 的 messages/tools/values 等载荷。Runtime v3 探针已确认：在 `wrap_tool_call` 的 `handler()` 返回后改写 ToolMessage，checkpoint 可保存改写结果，但 `tools/tool-finished` 仍带原始输出；若在工具返回前完成引用化，事件只携带引用。因此媒体识别和保存必须落在平台 Runtime 的工具实现/执行出口，不能只依赖 handler 之后的 `ResultFilesystemMiddleware`。原工具的可见输出、模型得到的返回内容与 checkpoint 消息应基于同一引用化结果；模型侧再按调用需要解析引用。

这属于 LangChain/Runtime 调用时序，不是 GraphHarbor 业务缺陷。GraphHarbor 通用协议只负责传递序列化后的通用事件；不在其中识别媒体类型、重写工具载荷或增加平台快照 API。

内部模型参考媒体与正式发布成果物保持语义区分。复用 Workspace 不代表将所有读过的附件、子任务材料自动放进成果物列表；预览权限不得扩大现有消息可见范围。

### 3.2 模型调用视图临时恢复媒体

持久化状态与单次模型输入分离。Runtime 在模型调用路径把引用解析成当前 Provider 支持的媒体块，必要时在内存中构造 Base64；不得把该临时展开结果写回消息状态或向浏览器公开。

- 首次读图后的下一次推理、后续追问、子图和已启用的模型切换均须验证。
- 不把本机文件路径当作远端 Provider 可访问 URL；不依赖新建公开链接或签名服务。
- 沿用当前上下文选择和预算规则，本期不另做“哪些历史图片值得再看”的策略系统。
- 引用缺失、校验失败或格式不支持时给出明确错误，不能静默丢图后继续声称模型已看图。
- 不承诺模型视觉 Token 或费用下降；本期保证媒体语义不丢失，并减少持久化与前端传输中的内联字节。

### 3.3 API 保持现有读取与鉴权边界

通过现有 GET `/threads/{id}/state` 读取当前快照；POST `/threads/{id}/history` 用于用户打开历史、分支定位或确有必要的有界详情查询，不使用初稿的 GET history 查询形式。

沿用 Thread/项目权限和 Workspace 读取能力，补齐新引用投影、预览所需的最少字段。若现有接口足够，则无需新增端点；不预设 `/workspace/blobs/{artifact_id}`，不为旧会话开发瘦身代理，也不新增整套 Transcript 数据库。

主快照、Thread 详情与公开事件必须对同一种新引用有一致语义；保持私有状态、子任务私有内容和错误脱敏边界。图片按需获取；预览失败不能令正文和步骤消失。

### 3.4 前端快照优先，控制器仍是实时状态事实源

先消费当前权威快照，再由现有 SDK 接管后续运行事件。主页面不绕过现有 Transcript 过滤、命名空间隔离、工具结果关联和分支逻辑直接拼 DOM。

| 情况 | 展示与连接动作 |
|---|---|
| 状态尚未核实 | 可展示当前用户/项目的缓存；不能把未知当作已完成；完成权威状态核对 |
| Thread idle，且已核实无活跃 Run、无待审批 | 展示当前快照，暂停无必要的内容回放；继续提交时由同一控制器开启订阅 |
| Thread busy，或 Run pending/running | 快照初始化后接续事件；保持消息 ID 和顺序，覆盖订阅交接窗口 |
| 存在 interrupt / 待审批 | 展示快照与审批信息，保持恢复和事件观察能力；不得当作普通完成态关闭 |
| Run success/error/timeout，或停止已确认 | 展示最终快照与实际终态，按 Thread/队列最新状态判断是否仍需观察 |
| 新会话遭遇网络中断、游标过期 | 使用现有恢复入口重新核实状态，不自动重投用户输入 |

Thread 状态是 idle/busy/interrupted/error；Run 状态是 pending/running/error/success/timeout/interrupted，不混用。

快照与事件交接要求：

- 使用现有 checkpoint、Run、namespace、事件序号/游标和消息 ID；不能仅按消息条数或到达时间判断新旧。
- 同一会话的新 Run 和分支必须重新确定边界，不能只比较不同分支的 step。
- 旧事件不得把完整答复刷成半截；也不得因去重丢弃真正的新消息、审批或终态。
- “只更新增量”约束界面更新结果，不承诺服务端完全不传历史事件。
- 前台重新进入、重新聚焦和已有后台通知触发状态核对；跨页面/后台发起运行的发现继续复用现有机制，不建立新的轮询系统。
- 根快照负责主对话；子任务卡片及展开详情继续走现有 scoped 路径，不声称根 messages 包含所有子图细节。

T01 用可控时序验证“读取快照期间运行开始/结束”“订阅之前已产生事件”“旧快照延迟返回”。无法通过现有协议保证正确性时，不以丢消息换取性能。

## 四、性能口径

唯一验收口径见 [verification.md](verification.md)。删除任意会话固定小于 20/30/50KB、端到端 50ms 和零重绘的承诺。

分别测量：冷打开、已有缓存切换、数据就绪到稳定绘制、媒体加载完成、内部读取与浏览器传输。正文/折叠步骤可用不等待图片全部加载；不通过删除历史文字或省略步骤达成体积指标。

## 五、实施顺序与标准同步

1. T01：完成 SDK/GraphHarbor 现有能力核对；继续建立新建基线夹具、请求画像和快照/事件竞态测试。
2. T02：冻结 Runtime 工具返回前的媒体引用契约与模型恢复最小闭环，并覆盖 checkpoint、公开事件及存储生命周期。
3. T03–T05：分别完成前端快照、Runtime 媒体和 API/Web 预览接线；按依赖收口。
4. T06–T07：整链路功能、性能、权限及失败恢复验收，更新进度和生效规范。

本次文档修订不将草案行为写成生效标准。实施时核对 `docs/standards/sse-event.md`、服务规范与新行为的关系；只同步实际改变的约束，不修改 GraphHarbor 外层 event/id/seq/namespace 契约。

仅在以下情况再次讨论：
1. 经证明存在 GraphHarbor 通用 Agent Server 缺陷，平台侧按既有 Runtime/SDK 能力无法解决，且需要修改其源码、版本、表结构或通用协议。方案须不含平台业务概念，并遵循 GraphHarbor 评审、双包锁步验证和发布规范。
2. 必须新增基础设施、扩大外部访问权限，或削减现有模型/媒体功能才可实现。
3. 在现有边界内无法满足已冻结验收目标，需用户决定调整目标或范围。

遇到上述情况，提交失败证据、已尝试的边界内替代方案及影响，暂停依赖该决定的任务，其余已授权工作继续。不得自行突破边界或降低验收标准。
