# F17 项目知识检索评估与 MCP 后续接入

## 项目概述

- **启动日期：** 2026-10-10。
- **目标：** 核实 DeerFlow 的知识能力，区分已有底座和真实缺口，决定是否开发 F17，避免重复建设 RAG 系统。
- **负责人：** AI 负责代码盘点与规划；用户负责范围决定；后续如涉及前端，由同事实施。
- **模板类型：** 标准模板。入库、检索、权限和引用属于同一条依赖链，不拆成独立子项目。
- **状态：** 本轮评估与前端交接已完成；用户确认 F17 本期不开发，功能 `deferred`；后续 MCP 接入尚未立项或授权。
- **改动级别：** 本轮仅文档。原 F17 如实施，涉及数据模型、外部服务、隔离与留存，属于治理改动，须人工评审。
- **预计工作量：** 当前没有开发排期；不沿用缺少前提的“2–3 周”承诺。未来先做供应商和实际接线核验，再估算。

## 当前结论

**用户已确认本期不开发同事提出的自建知识库；有真实知识 MCP 后，优先复用现有接入底座。**

用户已补充：当前没有企业知识检索服务；若改动很大就不做，后续倾向接入支持 MCP 的服务。2026-10-10 用户明确要求将“不开发”结论及前端交接合入 `feat/langgraph-v3-delta-evaluation`。这确认了当前范围，不代表批准未来 MCP 接入的实现。

理由如下：

1. 本地 DeerFlow 接的是外部 RAGFlow；它的知识路由是只读目录，不负责文档上传、切片、Embedding 或向量库运维。另有可选 LightRAG 检索接入。
2. 当前平台已有 MCP、工具策略、项目/Thread 身份、附件解析和个人记忆；缺少项目知识检索，但没有理由为能力清单完整性自建整套文档产品。
3. MCP 可以复用工具传输和装配；文档入库、检索质量、权限隔离仍需由实际知识服务承担，不能由协议名称推断完成。
4. 旧知识库产品曾明确退役。本方案不恢复旧服务、旧 API 或旧前端，不同时维护原生 `search_knowledge` 与相同知识源的 MCP 工具。
