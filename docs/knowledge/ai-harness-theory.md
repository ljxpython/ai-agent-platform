# AI Harness：让 AI 在你的项目里真正可靠工作

> 这不是一篇教你写更好的 Prompt 的文章。这是一篇关于如何给 AI 建立完整工作环境的文章。

---

## 一、你有没有遇到过这些情况

你告诉 AI："按我们的规范来，改完之后更新文档。"

AI 点头（比喻），改完代码，文档没更新。

你又说一遍。下次还是这样。

或者：你和 AI 讨论了半小时，敲定了一个架构决策，新开一个会话继续，AI 完全不知道之前说了什么，一切从零开始。

或者：AI 说"我按照流程做完了"，但你翻了半天找不到任何验证记录，不知道它到底做了什么，做没做完，做对没做对。

这些不是 AI 的能力问题。这是**运行环境**的问题。

---

## 二、Prompt 工程 ≠ AI Harness

大多数团队在 AI 集成上止步于 Prompt 工程——写一个很长的系统提示，列一堆规则，希望 AI 照着做。

这种做法有效，但上限很低。

| | Prompt 工程 | AI Harness |
|---|---|---|
| 关注点 | 怎么向 AI 提问 | AI 在什么环境里工作 |
| 作用范围 | 单次对话 | 跨会话、跨任务、跨团队 |
| 可维护性 | 一个人改 Prompt，影响全局 | 分层设计，按需修改 |
| 可验证性 | AI 说做了，你只能信 | 输出文件即验证证据 |
| 类比 | 给员工发一封好邮件 | 设计完整的团队协作制度 |

**AI Harness 的定义：** 让 AI 在你的项目里可靠、可观测、可迭代工作的完整运行环境。

它不是单一的提示词，而是一套系统设计——包含约束、流程、工具、记忆、监控、反馈六个层次。

---

## 三、六层架构

```
┌─────────────────────────────────────┐
│  约束层（Constraint Layer）          │
├─────────────────────────────────────┤
│  流程层（SOP / Skill Layer）         │
├─────────────────────────────────────┤
│  工具层（Tool Layer）                │
├─────────────────────────────────────┤
│  记忆层（Memory Layer）              │
├─────────────────────────────────────┤
│  可观测层（Observability Layer）     │
├─────────────────────────────────────┤
│  反馈层（Feedback Loop Layer）       │
└─────────────────────────────────────┘
```

这六层从下往上逐层依赖：没有约束，流程就是空文；没有记忆，流程每次都要重建；没有可观测性，你永远不知道 AI 有没有真的按流程执行；没有反馈，Harness 只会越来越厚，越来越难维护。

我们逐层拆开说。

---

## 四、约束层——规定 AI 的行为边界

### 是什么

约束层是 AI 工作的"宪法"——规定什么能做，什么不能做，遇到什么情况走什么流程。

在实践中，它通常是一个放在项目根目录的文件，Antigravity 里叫 `AGENTS.md`，其他 AI 工具里可能叫 `CLAUDE.md`、`CURSOR_RULES` 或类似的东西。

### 没有它会怎样

AI 会按自己的"直觉"工作。每次对话的行为不一致，今天改了一个 bug 顺手重构了一堆不相关的代码，明天又漏掉了文档更新。你不能怪 AI——它不知道你的项目有什么特殊要求。

### 怎么设计

**1. 改动分级，而不是一刀切**

这是约束层最重要的设计决策。不同规模的改动，需要不同重量的流程：

- **单服务内改动**：直接改代码 → 跑测试 → Commit，不需要任何额外文档
- **跨服务改动**：先规划 → 建项目文档 → 实现 → 验证
- **架构/生产/安全级别改动**：规划 → **人工评审批准** → 实施 → 全面验证

用"影响范围"而不是"代码量"来判断级别。改一行代码如果影响了服务间的接口契约，就是跨服务改动，不能按单服务处理。

**2. 反模式比规则更有效**

这是我反复验证过的一个洞察。

写"AI 应该在改动前先判断级别"，效果不如写"AI 不得在未建项目文档的情况下开始写跨服务改动的代码"。

前者是建议，后者是禁令。禁令对 AI 的约束力更强，因为它描述的是一个明确的"不合法状态"，而不是一个方向性的指引。

建议维护一个"严禁行为"列表，上限 10 条。超过 10 条说明这个层级承载了太多东西，应该往下沉到流程层或反馈层。

```markdown
## 严禁行为
- ❌ 不得在未建任务列表的情况下开始写跨服务改动的代码
- ❌ 不得把阶段性测试结果记录在最终验证区块里
- ❌ 不得自己批准架构级改动，人工评审是必须的
- ❌ 不得编造测试结果
```

**3. 结构化优于散文**

AI 解析结构化规则比解析散文可靠得多。同样的规则，列表 > 段落，决策树 > 列表，代码块中的示例 > 纯文字描述。

## 五、流程层——封装标准操作 SOP

### 是什么

如果约束层是"宪法"，流程层就是"法规实施细则"。它把常见的工作场景封装成标准操作流程（SOP），AI 按需读取和执行。

在实践中，每个 SOP 是一个独立的 `SKILL.md` 文件，描述：触发条件、工作步骤、文档模板、常见问题。

### 典型的三段式流程

一套能覆盖大多数开发场景的最小流程集合：

**plan-project（规划）**
- 触发：判断为跨服务改动或架构改动时
- 产出：项目文档目录，包含概览、方案、任务列表、验证计划

**implement-feature（实现）**
- 触发：项目文档存在，开始写代码时
- 产出：任务完成卡（包含改动内容、代码位置、预期结果、验证项、合规检查）

**verify-change（验证）**
- 触发：所有任务完成后
- 产出：验证记录，含四态判定（done / partial / blocked / deferred）

四态判定比"通过/不通过"实用得多——"blocked"表示有外部依赖卡住了，"deferred"表示这部分明确推迟而不是遗漏，让项目的真实状态不会被掩盖。

### 关键设计洞察

**Skill 是被 AI 主动读取的手册，不是自动触发的插件。**

这意味着触发条件必须写得足够明确，让 AI 能可靠地识别"现在该读这个 Skill 了"。模糊的描述会导致该用的时候没用，或者不该用的时候乱用。

**流程层和约束层不要信息重复。**

约束层说"跨服务改动需要建项目文档"，流程层说"项目文档长这样、怎么建"——两者分工不同，不要在两个地方写同样的内容。重复的信息久了必然漂移，产生矛盾。

### 任务结构的设计

任务列表里每个任务，应该能独立回答四个问题：

```markdown
### Task 1.1: 重构数据模型
- **改动内容：** 将 RuntimeConfig 重构为 dataclass 结构
- **代码位置：** `src/models.py` → `RuntimeConfig`
- **预期结果：** 支持新的配置格式，向后兼容旧版本
- **验证项：** `pytest tests/test_runtime_config.py` → 全部通过
```

这四个字段缺一不可。没有"预期结果"，你不知道改完应该是什么样；没有"验证项"，任务完没完全靠感觉。

## 六、工具层——AI 的能力边界

### 是什么

工具层定义了 AI 能做什么：读文件、写文件、运行命令、调用外部 API、启动子 Agent。

这一层通常不需要大量设计，AI 平台的内置工具已经够用。但有两个点值得重视。

### 危险操作守卫

AI 执行高风险操作前必须有人工确认机制。这不只是"AI 要先问我"，而是要在 Harness 里明确定义什么是高风险操作：

- 删除文件/目录
- `git push`、`git reset --hard`
- 数据库结构变更
- 调用生产环境 API

没有守卫机制，某天 AI 在自以为正确的情况下执行了一个不可逆操作，会造成难以挽回的后果。

### MCP 工具扩展

Model Context Protocol（MCP）允许你给 AI 添加自定义工具。当项目有专属操作——比如"查询特定服务的健康状态"、"触发内部 CI 流程"——可以通过 MCP 封装，让 AI 能直接调用而不是靠模糊的命令拼接。

工具层是扩展性最强的一层，随着 MCP 生态的成熟，这里能做的事会越来越多。

## 七、记忆层——最容易被忽视的层

### 核心问题

**AI 没有跨会话的持久记忆。**

每次新开一个对话，AI 都是白板状态。上次讨论的架构决策、上次确认的技术选型、项目现在处于什么阶段——全部不知道。

这不是 AI 的 bug，这是它的设计。问题在于大多数团队没有为此做任何补偿设计。

### 文件系统就是记忆

解法比你想象的简单：**把 AI 需要知道的东西写进文件**。

AI 每次新会话前读这些文件，记忆就被"恢复"了。

项目记忆可以分三类：

| 记忆类型 | 类比人类记忆 | 存放位置 | 内容 |
|---|---|---|---|
| 语义记忆 | 知识 | `FEATURES.md` | 项目现在有哪些功能 |
| 情节记忆 | 经历 | `projects/` | 具体做了什么、为什么这么做 |
| 程序记忆 | 习惯 | `Skills/` | 遇到 X 场景该怎么做 |

### CONTEXT.md：会话同步快照

在上述基础上，建议维护一个专门给 AI 消费的状态快照文件 `CONTEXT.md`：

```markdown
# 项目当前状态

## 最后更新
2026-09-21 | 完成数据建模重构

## 各服务状态
| 服务 | 状态 | 注意事项 |
|---|---|---|
| runtime-service | 稳定 | 新 API 需向后兼容 v1 |
| platform-api | 进行中 | 鉴权重构，预计本周完成 |

## 近期关键决策
- 09-18: 选择 dataclass 而非 Pydantic（性能考虑）
- 09-21: 引入两阶段验证机制
```

这个文件的维护规则：**只保留"当前有效"的信息，过期内容删掉，不要堆历史。** 历史在 `projects/` 和 `changes/` 里，`CONTEXT.md` 只是当前快照。

在约束层里加一条规则：每次新会话开始前读 `CONTEXT.md`，改动完成后更新它。

## 八、可观测层——你不知道 AI 有没有按流程走

### 核心问题

AI 说"我按照规范做完了"——你相信吗？

大多数人只能选择相信，因为没有别的办法。这是可观测性缺失的典型症状。

### 关键洞察

你观测不了 AI 的内部推理过程，但你能观测它的输出产物。

**把合规性体现在输出文件里，而不是依赖 AI 的口头声明。**

### Task Completion Card

每个任务完成时，要求 AI 输出一张完成卡：

```markdown
### Task 1.1: 重构 RuntimeConfig ✅ 2026-09-21
- **改动内容：** 重构为 dataclass 结构
- **代码位置：** `src/models.py` → `RuntimeConfig`
- **预期结果：** 支持新格式，向后兼容 v1
- **验证项：** `pytest tests/test_runtime_config.py` → ✅ 12/12 通过
- **合规检查：**
  - [x] 代码实现完成
  - [x] 验证项已执行
  - [x] 任务列表状态已更新
  - [ ] CONTEXT.md 已更新（此任务未涉及服务状态变化，跳过）
```

这张卡的意义：**你看一眼就知道这个任务做了什么、结果是什么、有没有经过验证、有没有遗漏该做的事**。

没有完成卡 = 任务没完成。这是硬规则。

### 状态一致性检查

项目结束时，要求 AI 做一次四处状态一致性检查：

- 项目概览文件的"状态"字段
- 任务列表的完成情况
- 验证记录的最终结论
- `CONTEXT.md` 里该项目的状态

四处必须一致，有任何不一致，先对齐再收尾。

这一步能捕捉到大量"代码改完了但验证记录没写"或"验证记录说通过了但任务列表还在进行中"的情况。

### 两阶段验证

另一个常见问题：每改一小块就跑全量测试，效率极差；什么都不测，心里没底。

解法是两阶段验证：

- **Phase 验证**（每个任务完成后）：只跑这个任务直接相关的最小测试集，验证改动本身不出错
- **Final 验证**（所有任务完成后）：全量单元测试 + 集成测试 + E2E

这样既保证了每步有验证，又不把所有时间花在等待全量测试上。

## 九、反馈层——让 AI 从错误中学习

### 核心问题

AI 犯了一个错，你纠正了。下次新会话，AI 还会犯同样的错。

这是 AI 无持久记忆的另一个后果。你的纠正没有写进任何地方，等于消失了。

### 三层经验库设计

**Tier 1：约束层的"严禁行为"（始终加载）**

上文提到的那个列表。放任何场景都不能做的事，不超过 10 条。这些是最高优先级的教训，每次对话都加载。

**Tier 2：领域经验文件（按需加载）**

```
docs/lessons/
├── index.md              # 索引，有哪些经验文件
├── runtime-service.md    # runtime 服务踩过的坑
├── api-design.md         # API 设计踩过的坑
└── ai-workflow.md        # AI 工作流本身踩过的坑
```

每条经验极简，不超过 4 行：

```markdown
## [坑] 模板升级时旧文档未标废弃

- **场景：** 从标准模板升级为多专题模板时
- **错误：** 只建了新文档，旧文档原地保留，读者不知道该看哪个
- **正确：** 旧文档顶部加废弃标注，README 的导航列表是唯一入口
- **日期：** 2026-09-21
```

在约束层里加规则：处理某个服务的改动前，读对应的 `lessons/{service}.md`（如果存在）。

**Tier 3：Git 历史 + ADR（永不主动加载）**

完整的错误对话、详细的决策背景——放这里，人工需要深挖时查阅。

### 蒸馏而非搬运

这是这个设计里最重要的原则：

**不要把完整的错误对话复制进经验文件。只提炼教训。**

完整错误对话可能有几千字，加载进上下文会消耗大量 token，还很难快速抓住重点。蒸馏成 4 行，信息密度高得多，加载成本可以忽略。

### 新坑的沉淀流程

```
AI 犯了错 → 你纠正
    ↓
AI（或你）蒸馏成 ≤4 行
    ↓
判断级别：
  任何场景都会犯 → 写进严禁行为（≤10条上限）
  特定领域才会犯 → 写进 docs/lessons/{domain}.md
    ↓
更新 lessons/index.md 的条数
```

## 十、六层的依赖关系

这六层不是独立的，有明确的依赖和协作关系：

```
约束层  ──▶  规定"什么情况走什么流程"
流程层  ──▶  告诉 AI "这个流程具体怎么走"
工具层  ──▶  提供"走这个流程需要的能力"
记忆层  ──▶  让 AI 知道"当前项目处于什么状态"
可观测层 ─▶  让你知道"AI 有没有真的按流程走"
反馈层  ──▶  把错误转化为下次的约束，形成闭环
```

六层缺任何一层，系统都会有明显的薄弱点：

| 缺失层 | 症状 |
|---|---|
| 缺约束层 | AI 行为不一致，每次对话像第一次合作 |
| 缺流程层 | 有规则但没有操作路径，AI 做事效率低 |
| 缺记忆层 | 每次新会话重建上下文，大量时间浪费在"同步状态" |
| 缺可观测层 | 不知道 AI 有没有真正按规范工作，只能信任口头声明 |
| 缺反馈层 | 同样的错误反复发生，团队在 AI 上的投入没有积累 |
| 缺工具层 | AI 能力受限，很多事情"想做但没有手" |

## 十一、从零开始的迭代路径

不要一次性建全。按以下优先级迭代，每一步都有明确收益：

**阶段一（第 1 周）：建约束层**

写一个 `AGENTS.md`，包含：
- 项目是什么、有哪些服务/模块
- 改动分级规则
- 严禁行为列表（先列你最在意的 3-5 条）

**立刻可见的收益：** AI 不再每次行为不一致。

**阶段二（第 2-3 周）：建流程层**

写三个最简单的 Skill：规划 / 实现 / 验证。

哪怕每个 Skill 只有 15 行，也比没有强。关键是把流程固化下来，不靠每次口头指定。

**立刻可见的收益：** 跨服务改动有了可跟踪的项目文档。

**阶段三（第 1 个月）：建记忆层**

建 `CONTEXT.md`，在约束层里加"每次新会话读这个文件"的规则，养成改完就更新的习惯。

**立刻可见的收益：** 新会话不再需要重新介绍项目背景。

**阶段四（持续迭代）：建反馈层**

每次犯错，蒸馏一条教训进 `lessons/`。这不是一次性建好的层，而是随项目生长的层。

**长期收益：** AI 在你的项目里犯的错越来越少，经验库越来越有价值。

**按需扩展：可观测层**

当你开始觉得"AI 说做完了但我不确定"，这时候加 Task Completion Card 和状态一致性检查。

---

## 十二、结语：Harness 是工程问题，不是玄学

AI 在你的项目里工作不可靠，不是因为 AI 能力不够，而是因为我们没有给它一个可靠的工作环境。

一个没有规范的人类工程师会乱——AI 同样会。区别只是，给人类工程师建立工作规范需要面谈、文化建设、长期磨合；给 AI 建立工作规范可以写进文件，版本控制，立刻生效。

这是 AI 的优势，也是我们常常忽视的机会。

Harness 的本质是：**把你对 AI 工作方式的期望，从口头说说变成可执行、可验证、可迭代的系统。**

从约束层的第一条规则开始写起。你会发现，AI 在项目里的表现会以你没预料到的速度变好。
