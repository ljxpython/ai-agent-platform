# 核心架构原则与设计权衡

设计一个大型系统，技术选型只是表象，背后的**设计原则**才决定了代码会不会越写越乱。在这个平台中，有四条贯穿所有子模块的核心原则。

---

## 原则一：控制面与执行面物理隔离

系统严格区分两件事：“你在平台里是谁、能干什么” 与 “Agent 这一步具体怎么跑”。

- **控制面（`platform-api`）是裁判**：管组织架构、权限分配、审计记账、大模型配置目录。它不关心大模型具体的 Prompt 怎么写，也不关心某个 Python 工具怎么运行。
- **执行面（`runtime-service`）是选手**：只专注跑图、调模型、执行工具。它甚至不需要知道当前操作人叫什么名字，只要请求带着合法的内部凭证，它就只管执行。

**带来的直接好处**：
就算 Runtime 因为某个写得糟糕的外部工具跑飞了、或者内存耗尽被操作系统杀死，平台的管理后台、用户登录和权限系统依然稳如泰山，完全不受影响。

---

## 原则二：零信任短时凭证（Delegation JWT）

在微服务通信中，最忌讳的做法是把前端用户的登录 Token 从头透传到尾，或者干脆服务之间不设防。

本系统采用**短时委托机制**：
1. 前端向 API 发起请求，证明“我是合法登录的用户”。
2. API 查验该用户是否有权操作目标智能体、是否在目标项目内。
3. 查验通过后，API 临时签发一张只有 **60 秒有效期** 的专用小票（Delegation JWT）。
4. 这张小票上明确印着：允许执行的操作类型（例如只允许读状态，不允许新建 Run）、允许调用的模型白名单、以及目标项目 ID。
5. Runtime 收到小票后只验小票签名与有效时间。

**带来的直接好处**：
即便某一次请求的凭证在传输过程中被意外记录在日志中，60 秒后它就变成废纸一张，攻击者无法拿着它去进行长期越权操作。

---

## 原则三：有向状态图与检查点机制（Checkpoints）

传统的 API 通常是“请求进来 -> 同步处理 -> 响应返回”。但是一个复杂的 Agent 任务往往持续数分钟，中途还会发生大模型网络波动，甚至需要暂停并等待人类审批。

为了应对这种情况，执行面把每一次任务都建模成 **LangGraph 状态图**：
- 任务执行的每一步（大模型思考、工具调用、等待确认）都会落库成一个**检查点（Checkpoint）**。
- 如果执行到第 5 步时服务器意外断电重启，系统不需要从第 1 步重新开始跑，直接从第 4 步的检查点恢复状态即可继续执行。
- 当智能体需要危险操作（如删除数据库、给外部发邮件）时，状态机直接挂起，将控制权转为人机协作（HITL），等待用户在前端点击“批准”后，再从原位置继续流转。

---

## 原则四：连接状态与运行状态解耦

前端使用 SSE（Server-Sent Events）接收流式输出时，很多新手代码经常犯一个错误：**一旦网络波动断网，就以为任务执行失败了**。

本系统的核心原则是：**网络连接是网络连接，任务运行是任务运行，两者必须分清楚**。

1. **连接断了不代表 Run 失败**：
   如果用户的笔记本合上盖子或 WiFi 断开，后台的 Runtime Worker 依然在数据库和模型之间稳步执行，任务并没有中断。
2. **重连自愈机制**：
   当用户恢复网络时，前端会自动向 API 发起状态轮询与事件补录。如果之前的事件游标已经过期（返回 HTTP 410），前端能自动降级拉取最新快照，并在界面上恢复审批状态，不需要用户刷新整个网页重来。
