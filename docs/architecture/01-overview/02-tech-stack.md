## 核心选型深层逻辑（为什么不用其他方案？）

### 1. 为什么是 LangGraph，而不是单纯的 LangChain Chain？
单纯的 LLM Chain 只能一条道走到黑（输入 -> 提示词 -> 模型 -> 输出）。但真实的工业级多智能体往往需要**循环思考、工具调用失败后自适应重试、甚至中途挂起暂停等待人类审批（Human-in-the-loop）**。
LangGraph 本质上是一个**有状态的有向图（StateGraph）**。它把执行过程每一步的状态都增量记录进持久化存储。哪怕宿主容器崩溃、网络闪断，也能从上一个保存点（Checkpoint）重新加载恢复执行，上下文绝不会丢，这是不可逆的线性 Chain 根本做不到的。

### 2. 为什么选择独立自研 Runtime Gateway，而不是 Nginx 直接反代？
如果只用普通反向代理（如 Nginx），它只负责在 TCP/HTTP 层面转发字节流，完全不理解 LLM 交互与智能体业务逻辑。
平台内部自研的 `runtime_gateway` 在转发时承担了三项 Nginx 无法处理的硬核职责：
1. **身份换签与权限沙箱化**：把前端的普通用户 Bearer Token 剥离，重新生成带有严格时效与操作范围的内部短时 Delegation JWT，杜绝前台凭证长驱直入底层服务。
2. **SSE 帧流式审查**：动态检测长连接返回的内容，如果发现单帧大小超过 8MB 阈值则主动阻断，防止模型发疯输出异常超大文本撑爆前端浏览器内存。
3. **心跳保活帧注入**：当大模型进行深度思考（Reasoning）长达数十秒不出字时，网关定时向下游注入 `: heartbeat` 空白帧，防止浏览器与中间网络代理触发 45 秒闲置超时断开。

### 3. 为什么业务库与运行状态库坚持物理一分为二？
将业务数据与执行状态分开，是为了**故障隔离与生命周期分离**：
- **业务库（Platform DB）**：存储租户、账号、组织架构与审计凭据，属于高价值、低频写、强一致性数据，需要长久保存且必须保证最高等级的可靠性与日常备份。
- **状态库（Runtime DB）**：智能体单次运行就会在数据库里留下数十次工具调用记录、巨大模型上下文快照（Checkpoints）和临时帧状态，属于典型的“海量写入、快速老化、定期清理”数据。
如果把它们塞在同一个 PostgreSQL 实例或同一个库内，一旦并发执行几十个复杂 Agent，突发的高频快照写入会瞬间吃满 IOPS 和连接池，导致前台正常用户连登录页面都打不开！

### 4. 为什么是 Loki + Prometheus 双轨制，而不是笨重的 ELK/SkyWalking？
很多团队一做微服务排障，脑子一热就直接上 ElasticSearch + Logstash + Kibana（ELK），或者全套 Java 技术栈的 SkyWalking，机器一开就是 8GB~16GB 内存常驻，维护成本极高，资源极度浪费。
本项目采取**极度克制的轻量化可观测架构**：
- **Loki 不建文本全文倒排索引**：只对元数据标签（`service`、`trace_id`、`level`）建立轻量级 TSDB 索引，日志原始内容压缩成 chunk 分块存储在磁盘。
- **Prometheus 负责定量指标监控**：采集请求速率、错误率、分位延迟，向外暴露标准的 `/metrics`。
- 在生产主机实测部署中，**Prometheus + Grafana + Loki + Promtail 四容器常驻总内存仅约 186 MiB，CPU 占用 < 1%**！输入任意一个 `trace_id`，就能在毫秒级内直出跨三个微服务的结构化对齐日志瀑布流。

### 5. 为什么知识中台坚持“零隧道单向验签”，而不是 SSH/HTTP 反向代理穿透？
早期的跨网知识库方案经常使用 SSH 反向穿透隧道将远端私网环境暴露给主平台，存在三大工程缺陷：
1. **反向隧道极脆弱**：公网网络抖动或 SSH 断线会导致隧道假死，需要维护复杂的守护脚本去自愈重连。
2. **破坏网络安全边界**：将远端内网端口穿透暴露，严重违反生产合规审计要求。
3. **错误状态归因混乱**：穿透链路一旦报错，无法区分是 SSH 隧道挂了还是远端知识检索服务自身故障。
因此，平台全面演进为**零隧道单向入站自治架构**：基于 Scoped HMAC/JWT 动态签发短时凭据，远端只作为纯单向入站服务（仅需开放受保护端口），本地自治校验并返回标准 Envelope，彻底消灭对穿透隧道的反模式依赖。

### 6. 为什么持续评测飞轮（EvalFlow）拆分为独立服务与独立存储，而不是在 platform-api 业务库里直接加表？
很多团队图省事，把“评测”当成主业务的一个小模块，直接在业务库里建 `eval_tests`、`eval_runs` 表。这是极其致命的架构短视：
1. **算力与并发严重冲突**：真实生产评测是大规模批处理任务（单次飞轮评测可能包含数百个 TestCase，每个用例都要并发调用 LLM、甚至拉起真实沙箱与多轮 Agent 对话），会瞬时吃光网络连接与机器算力。
2. **数据资产隔离与独立自治**：评测集、评测结果与裁判评分（LLM-as-a-Judge）属于算法迭代和质量工程资产，具有独立生命周期。通过将 EvalFlow 拆解为独立服务（`5000/9128`）并接入独立的 MLflow 追踪，**EvalFlow 既可以与线上 Agent 跨机协同，也可以脱离主平台独立作为 CI/CD 自动化卡点或离线评测引擎运行**。
3. **零源码与环境侵入**：EvalFlow 运行评测时，只通过标准 API 和只读凭据向 Agent 发起执行与状态采集，严禁直接读取 Agent 的源码或共享虚拟环境，实现了两套系统物理级别的彻底解耦。

### 7. 为什么 AI 网关用量看板坚持 Vue 3 + ECharts 原生组件深钻，而不是在控制台嵌一个 Grafana iframe？
有些团队为了快速上线用量看板，直接在前端嵌入一个配置好的 Grafana 仪表盘 iframe。在工业级真实场景中，这会带来无法容忍的工程灾难：
1. **鉴权与多租户穿透泥潭**：Grafana 的多租户认证难以优雅地与平台的 RBAC 租户凭证打通，Cookie/JWT 跨域共享与反向代理极为脆弱，深浅色主题切换和移动端自适应更是难以协调。
2. **“指标 -> 日志 -> 会话追踪”无法形成闭环**：平台自研的 Vue 3 + ECharts 看板深度绑定了内部的 `trace_id` 与 Session 上下文。当运营人员或开发者点击时序柱状图的某一分钟异常毛刺时，系统能**毫秒级联动滑出右侧日志抽屉，直接拉出对应时间段内相关的 Loki 日志流与错误详情，甚至一键跳转至原始会话回放**。这种端到端的精细化下钻闭环，是任何通用 iframe 面板都无法实现的。
