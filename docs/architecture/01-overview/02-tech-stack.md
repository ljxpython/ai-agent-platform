# 统一技术栈全景与选型考量

了解一个复杂项目的技术栈，最忌讳只看名词清单。关键是要知道**为什么挑了这个库，它在整个盘子里解决什么问题**。

## 核心选型深层逻辑（为什么不用其他方案？）

### 1. 为什么是 LangGraph，而不是单纯的 LangChain Chain？
单纯的 LLM Chain 只能一条道走到黑（输入 -> 提示词 -> 模型 -> 输出）。但真实的复杂智能体往往需要**循环思考、工具调用失败后重试、或者中途暂停等待人类审批**。
LangGraph 本质上是一个**有状态的有向图（StateGraph）**。它把执行过程每一步的状态都存入数据库。哪怕程序中途崩溃，也能从上一个保存点（Checkpoint）重新加载并继续往下跑，不会丢失上下文。

### 2. 为什么选择独立自研 Runtime Gateway，而不是 Nginx 直接反代？
如果只用普通反向代理（如 Nginx），它只负责转发字节流，不懂业务逻辑。
平台内部自研的 `runtime_gateway` 在转发时要完成三件 Nginx 很难做的事：
1. **身份换签**：把前端的普通用户 Bearer Token 剥离，重新生成带有严格权限范围的内部短时 Delegation JWT。
2. **SSE 帧审查**：动态检测长连接返回的内容，如果发现单帧大小超过 8MB 则切断，防止恶意内容撑爆内存。
3. **心跳保活注入**：当大模型长时间思考不出字时，网关定时向下游注入 `: heartbeat` 空白帧，防止浏览器触发 45 秒超时报错。

### 3. 为什么数据库坚持一分为二？
将业务数据与执行状态分开，是为了**故障隔离与生命周期分离**。
平台的租户、账号是高价值、低频写的数据，需要长久保存且定期备份。
而 Agent 每次运行都会在数据库里留下几十次工具调用记录和大量上下文快照，属于典型的“海量写、快速老化”数据。
把它们放在同一个库里，一旦并发执行几十个复杂 Agent，大量快照写入会抢占连接池，直接让前台用户连登录页面都打不开。
